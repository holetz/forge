## Problem

A shared server needs controls the local profile does not: every egress through a proxy that injects tokens, telemetry and session logs that close Omnigent's audit gap, and a registry of the MCP servers. Ship the server profile on a Linux VM, sized for 30 concurrent sessions.

Member S14 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A server profile exists as an overlay on the local compose (`compose.server.yaml`, used as `-f compose.yaml -f compose.server.yaml`): same Omnigent, Postgres, Dex, router and stub, plus the pieces below.
- Every egress from an agent goes through one egress gateway that holds the upstream tokens and injects them; agent containers sit on an `internal` network with no route out, and their environment holds no credential.
- Model calls reach the gateway through the router, which keeps its task routing but no longer holds a real token.
- An OpenTelemetry collector receives OTLP from runners and the gateway's audit records, and writes them to a file sink; one audit record answers who, which upstream and model, how many tokens, what status.
- An MCP server registry lists the approved servers, how an agent reaches each one (always through the gateway) and which roles may use it; a test fails when a registry entry has no gateway upstream.
- A reasoned sizing for 30 concurrent sessions is written down, with a light concurrency probe against the stub whose numbers are recorded; no saturating load test exists.
- `scripts/smoke-server.sh` proves all of it offline against the stub and is wired, with the unit tests, into `scripts/verify_repo.sh`.

## Out of Scope

- Any paid or Databricks call, and the live check against Unity Gateway through the gateway: a human step in `## Handoff`.
- TLS interception (a CONNECT proxy that rewrites HTTPS) and a host firewall for the server-side containers: rejected in `## Design`; the firewall is a deployment step for the adopter's VM.
- Cost per person, team and session, budgets and alerts (S21); the audit record carries token counts only.
- The policy pack (S16) and the overlay contract for a private distribution (S15).
- A Postgres sink for telemetry: the collector has no Postgres exporter; a file sink is shipped and the choice is argued in `## Design`.
- Provisioning the VM, a real IdP, a real MCP server and real hostnames: the registry ships placeholders only.
- Changing `.github/workflows/ci.yml` or adding any permission grant.

## Design

### Mapa de dependências

The repository is small. `compose.yaml` is the base the overlay extends: the overlay moves `stub` off the `default` network, repoints the router's three upstream variables, and adds services; nothing in the base changes. `local/router/router.py` hard-codes `STUB_HOST = "stub"` as the only plain-HTTP upstream; the gateway is a second internal host, so this is the one base file that must change, and `local/router/test_router.py` pins the rule. `scripts/verify_repo.sh` is run unchanged by CI, so steps added there reach CI without touching `ci.yml`. `scripts/smoke-local.sh` is the pattern for the new smoke (disk guard, image bookkeeping, teardown trap) and is not edited; the two smokes use different compose project names (`forge-smoke`, `forge-server-smoke`) so neither can delete the other's volumes. Nothing orphans if the overlay changes. (2026-10-25)

### Stack

```
agents network (internal: no route out)        default network            upstream network (NAT out)
  agent-probe / runners ─► egress :3128 ◄───────── router :4000 ◄── omnigent
        │  OTLP                │  audit file          │
        ▼                      ▼                      │
  otel-collector ◄── audit volume (read-only)         │
        │ file exporter                         egress ──► stub (smoke) | Unity Gateway | MCP | git
        ▼
   telemetry volume                  mcp-registry :8090 (read-only JSON)
```

Images (pinned by tag and digest, verified 2026-10-25): the collector is `otel/opentelemetry-collector-contrib:0.163.2@sha256:7f22d2a6748110ffb6a59bc0df448bccbf501cdb667d610ede4c61d3863d5849` (Apache-2.0, 116 MB compressed for amd64, below the 500 MB line; the contrib build is needed for the `filelog` receiver and the `file` exporter, the core build has neither). The egress gateway and the registry are stdlib Python scripts on the already-pinned `python:3.13-alpine`, so they add no image. The overlay reuses the base file's pins for everything else.

### Egress gateway

One stdlib script, `server/egress/egress.py`, a **reverse gateway** not a CONNECT proxy. A caller addresses `http://egress:3128/u/<upstream>/<path>`; `<upstream>` must be a key of `server/egress/upstreams.json`, which names, per upstream, the environment variables holding its base URL and its token (names only, no values). The gateway drops every client `Authorization` and `Proxy-Authorization`, adds `Authorization: Bearer <token>` (or the configured header), forwards over TLS, and streams the response back (SSE included). It refuses: an unknown upstream (403), an upstream whose base URL is unset (503), `CONNECT` (405), and a non-stub plain-HTTP base URL at start-up, the same rule as the router. Tokens exist only in the gateway's environment; the router, Omnigent and the runners hold placeholders.

Why a reverse gateway: injecting a token into HTTPS through a CONNECT proxy needs TLS interception, which means a private CA installed in every agent container and a decrypted copy of every payload in one process. The reverse form needs only a base-URL setting in each client (OpenAI-compatible clients, MCP clients and `git` with `url.<base>.insteadOf` all have one), keeps TLS end to end between gateway and upstream, and reads a request body only for the model upstream, to record the model name. The cost: a client that cannot be pointed at a base URL cannot be served, so such a client gets no route at all, which is the safe failure.

The enforcement that the agent cannot bypass the gateway by writing code is network topology, not the gateway: runners attach to `agents`, a network declared `internal: true`, whose only other member is the gateway. The smoke proves the probe container on `agents` cannot reach the stub or an outside address. Containers on `default` (Omnigent, router, Postgres, Dex) keep NAT out, because Docker does not publish ports of an internal-only network; closing that is a host firewall rule on the VM, documented as a deployment step and an ACCEPTED risk.

### Audit and telemetry

The gateway appends one JSON line per request to `/audit/egress.jsonl` on the `audit-data` volume: UTC time, request id, upstream name, method, path (no query string), status, bytes in and out, duration, the caller's `X-Forge-User` and `X-Forge-Session` headers when present, and for the model upstream the request `model` and, for a non-streamed JSON response, `usage` token counts. Never a header value, a token or a body. The collector tails that file with `filelog`, receives OTLP/HTTP on 4318 from runners and the harnesses that emit OpenTelemetry, and writes both pipelines to `/telemetry/*.jsonl` with the `file` exporter (rotation configured). Together: the gateway record says who asked which upstream and model with what result and size; the OTLP stream carries the harness's own session events. That closes the audit gap the epic names (`gateway + telemetry + session log`) without depending on an Omnigent audit log that is undocumented.

Sink: file, not Postgres. The collector has no Postgres exporter, a database sink would mean a second custom component, and a JSONL volume is ingestible by anything later (S21 will read it for cost). Reversible: swapping the exporter touches `server/otel/config.yaml` only.

### MCP registry

`server/mcp/registry.json` lists approved MCP servers: `name`, `description`, `transport` (`streamable-http`), `upstream` (a key of `upstreams.json`), `roles` (who may use it), `enabled`. `server/mcp/registry.py` serves it read-only (`GET /servers`, `/servers/<name>`, `/healthz`), and for each entry adds `endpoint: http://egress:3128/u/<upstream>/`, so a client learns the gateway URL and never the real one. The shipped entries are placeholders on `.invalid` hosts with `enabled: false`. A unit test fails on an entry whose `upstream` is missing from `upstreams.json`. Role enforcement at call time is Omnigent policy (S16); the registry is the inventory.

### Router change

`router.py` accepts plain HTTP only to hosts named in `FORGE_PLAIN_HTTP_HOSTS` (default `stub`); the overlay sets `stub,egress`. The router still drops the caller's `Authorization` and adds its configured bearer; in the overlay that bearer is a placeholder the gateway replaces.

### Sizing for 30 sessions

A reasoned estimate in `docs/server-sizing.md`, from stated assumptions: a runner container (harness plus toolchain plus a repository checkout) at 1.5 GB RAM and 1 vCPU burst; the Omnigent server, Postgres, Dex, router, gateway, collector and registry at about 3 GB together; headroom 25%; so 30 sessions need about 55 GB RAM and 16 vCPU, recommended VM 16 vCPU, 64 GB RAM, 500 GB SSD, with disk driven by checkouts and image layers. Gateway load: 30 sessions each holding at most one model call in flight, about 20 calls a minute per active session at the intense tier, so roughly 10 requests a second at peak, far under what a threaded stdlib process serves. The probe (`scripts/probe-concurrency.py`) runs 30 concurrent clients with 5 requests each (150 requests) through router and gateway to the stub, reports p50/p95/max latency and failures, and the smoke samples the gateway container's memory once. The stub answers instantly, so the probe measures the gateway and router overhead and the thread model, not model latency; the VM figures stay an estimate until the pilot (S25) measures real sessions.

## Alternatives Considered

- **mitmproxy or Squid with TLS interception.** Rejected: a private CA in every agent image, decrypted payloads in one process, and a larger image for Squid-with-ssl-bump or mitmproxy; the reverse gateway gives the same "token only at the proxy" with less trust.
- **Envoy or Caddy as the gateway.** Rejected: header injection from the environment and an audit line with the model name are a short script; Envoy's config surface and Caddy's would not be smaller, and neither records the model. They stay candidates if the gateway needs HTTP/2 or rate limiting.
- **LiteLLM as the gateway.** Rejected here for the same reason as in S13 (large image, routing and spend not wanted in the egress path); S21 decides whether it lives in the compose.
- **Langfuse for traces.** Rejected: ClickHouse, Redis and S3-compatible storage are the heaviest stack proposed; the collector plus a file sink is the lightest that closes the gap.
- **Docker MCP Gateway, MetaMCP or ContextForge as the registry.** Rejected for now: each runs and proxies MCP servers, a bigger surface than an inventory; the registry is JSON plus a read-only endpoint, and a heavier gateway can replace it behind the same file.
- **Postgres as the telemetry sink.** Rejected, see `## Design` §Audit and telemetry.

## Open Decisions

- **Whether the reverse gateway is enough for the adopter's clients** (the OpenCode runner, git over HTTPS, the Databricks SDK, MCP clients). Decided by the live checks in `## Handoff`; the fix for a client that cannot take a base URL is a per-client shim or, as a last resort, a TLS-intercepting proxy as a separate decision.
- **Host firewall for the server-side containers on `default`.** Left to the adopter's VM; this spec documents the rule and does not enforce it.
- **Real sizing.** The 30-session figures are an estimate; the pilot (S25) replaces them with measurements.
- **Omnigent upgrade policy** stays the epic's open decision; the overlay inherits the base file's pin.
- **Why now / not worth doing:** why-now is the epic's order (S14 gates S15 and S25); a reason to drop it would be Omnigent shipping its own egress control and audit log, which the pin and a thin overlay contain.

## Risks

- **Containers on `default` keep NAT out, so the gateway is not a hard wall for them:** the hard wall is the `agents` network where runners live. ACCEPTED — Docker cannot publish ports from an internal-only network; a host firewall closes it at deployment.
- **The gateway becomes a single point of failure and a high-value target (holds every token):** it is a small stdlib script, runs read-only with no published port, logs no secret, and its tests assert the client credential never reaches an upstream and no token reaches a log line.
- **A token or host leaks into the public repo:** placeholders and `.invalid` hosts only, `.env` ignored, the leak gate and Gitleaks in CI; fixtures use obviously fake values generated at run time; Gitleaks hits are fixed at the source.
- **The collector image is the largest pull:** 116 MB compressed, pinned by digest; the smoke removes it afterwards.
- **Audit file grows without bound:** the file exporter is configured with rotation; sizing in `docs/server-sizing.md` states the retention figure.
- **Sizing is an estimate:** stated as such, with its assumptions; the probe covers only the gateway path against an instant stub.
- **Disk pressure when pulling:** the smoke aborts below 8 GB free after the pull and removes what it pulled; tear-down runs `down -v` on exit.
- **Collector runs as root to write the volume:** limited to a private volume and no published port; recorded, not hidden.
