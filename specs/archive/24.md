## Problem

The batch review of 2026-10-25 covered PRs #18 to #22 and found five defects in what S34, S13, S37 and S14 shipped.

1. **Path escape with an injected credential (high).** `server/egress/egress.py:58` accepts any rest after `/u/<name>`, and `:152` concatenates it to the upstream base path without normalizing it. The conductor reproduced it: `split_target("/u/models-default/../../../api/2.0/token/create")` yields `/ai-gateway/mlflow/v1/../../../api/2.0/token/create`, and `%2e%2e` passes too. The gateway then sends the operator's upstream token to any route on the upstream host, for example a workspace REST API that creates a new token. Fix: refuse dot segments, raw or percent-encoded, and encoded slashes. Enforce that the resolved path stays under the upstream's base path. Add a per-upstream allowlist of methods and path prefixes to the upstream registry; the model upstreams allow only the chat and completions routes.
2. **Spoofable audit identity (medium).** `local/router/router.py:63-66` copies the client's `X-Forge-User` and `X-Forge-Session` headers, and `egress.py:123-124` records them. A runner on the `agents` network can also call `egress:3128` directly. Fix: the audit identity must come from something a runner cannot forge, such as a header the router signs with a secret shared only with the gateway, or network isolation so that only the router reaches the gateway. Develop picks the design. An unauthenticated identity is recorded as unauthenticated, never as the claimed value. Correct the contradiction in `egress.py:6` and `README.md:47`.
3. **Client credentials forwarded (medium-low).** `egress.py:22` strips only `Authorization`, so `Cookie`, `X-Api-Key`, `api-key`, `PRIVATE-TOKEN` and similar headers reach the upstream. Fix: forward through an allowlist of headers, not a denylist.
4. **`scripts/leak-generic.sh:19` fails open (low).** A `git grep` error (exit 2 or 128) prints `clean`. Fix: treat any exit other than 0 or 1 as a failure.
5. **Retention math (low).** `docs/server-sizing.md:33` says 500 MB per sink, but `server/otel/config.yaml:23-24` gives 550 MB. Fix the doc.

Done when unit tests cover each case: dot segments and encoded variants refused, method and path allowlist enforced, a non-allowlisted header dropped, a forged identity not recorded, and the `git grep` error path. `scripts/smoke-server.sh` also proves the identity path, and the gate and CI are green. No CI workflow or grant change.

Member of holetz/forge epic 1 (follow-up of S14 and S34).

## Proposal

- The gateway refuses a request whose path carries a dot segment or an encoded slash (raw, percent-encoded or double-encoded) before it dials the upstream; the resolved path is proven to stay under the upstream's base path.
- Each upstream in `server/egress/upstreams.json` declares the methods and path prefixes it accepts; the gateway answers 403 for anything else, and an upstream that declares none fails to load. The model upstreams accept only `POST` on the chat and completions routes.
- The gateway forwards only an allowlisted set of client headers; every other header (`Cookie`, `X-Api-Key`, `api-key`, `PRIVATE-TOKEN`, ...) is dropped.
- The audit `user` and `session` come only from an identity the router signed with a secret shared with the gateway alone. A request without a valid signature is recorded as `unauthenticated`, never as the claimed value. The `egress.py` docstring and `README.md` no longer claim the audit holds no header value.
- `scripts/leak-generic.sh` exits non-zero when `git grep` fails (any code other than 0 or 1) instead of printing `clean`.
- `docs/server-sizing.md` states 550 MB per sink, matching `server/otel/config.yaml`.

## Out of Scope

- Authenticating the end user at the router (validating the OIDC token): the signature proves a record passed through the router, not that the router's caller is who the header says. Follow-up, parked in Discoveries.
- Closing the direct runner-to-gateway path or changing the S14 network topology: git and MCP clients reach the gateway directly by design.
- Per-runner credentials or mTLS: a secret-distribution scheme the adopter would operate.
- Any CI workflow, grant or pinned-image change; the gate and workflow files are untouched.
- Response-side filtering and request body inspection.

## Design

**Rule 1: the path is validated, never normalized.** The gateway parses the request target itself (split on the first `?`; it must start with one `/`), then checks the rest after `/u/<name>`: it is percent-decoded repeatedly (up to three rounds) and, at every round, a segment equal to `.` or `..` (also with a `;params` tail), any `/`-equivalent (`%2f`, `%5c`, backslash), a NUL or control byte, a `#`, or an empty inner segment refuses the request (400). The raw rest is what is forwarded, so what was checked is what is sent. As defence in depth the joined path is also `posixpath.normpath`-checked to start with the base path.

**Rule 2: each upstream declares what it accepts.** `upstreams.json` gains an `allow` list of `{methods, prefixes}`; a prefix matches at a segment boundary, relative to the upstream base. The models upstreams allow `POST` on `/chat/completions`, `/completions`, `/v1/chat/completions` and `/v1/completions` (the router posts the `v1` form; the stub the bare form). `git` allows `GET, HEAD, POST` and `mcp-catalog` allows `GET, POST, DELETE` on `/` (the base path is the bound). An entry without `allow` raises at load: fail closed. `server/mcp/registry.py` reads only `upstream` keys and tolerates the extra field.

**Rule 3: forward an allowlist of headers.** Forwarded: `accept`, `accept-encoding`, `accept-language`, `cache-control`, `content-encoding`, `content-type`, `git-protocol`, `if-modified-since`, `if-none-match`, `last-event-id`, `mcp-protocol-version`, `mcp-session-id`, `pragma`, `range`, `user-agent`. `Authorization` and `Content-Length` are set by the gateway.

**Rule 4: identity is signed by the router, verified by the gateway.** The router sends `X-Forge-Identity: v1.<unix-ts>.<hex>` where the value is `HMAC-SHA256(secret, "v1\n<ts>\n<user>\n<session>")` over the identity headers it forwards. The gateway recomputes it over the received `X-Forge-User`/`X-Forge-Session`, compares in constant time and accepts a timestamp within 300 s. Valid: audit `user`/`session` take the cleaned values and `"identity":"router"`. Anything else, an unset secret included: `user` and `session` are the literal `unauthenticated` and `"identity":"unauthenticated"`. The secret (`EGRESS_IDENTITY_SECRET` in `.env`, `openssl rand -hex 32`) is passed to the router and the gateway only, never to a runner; an empty value disables signing and verification, and a value shorter than 32 characters refuses to start. `.env.example` leaves it empty so no known secret ships. The sign and verify helpers are duplicated in the two stdlib-only services, locked together by one shared test vector.

**Rule 5: the audit docstring and README say what the audit holds**: never a credential or a body; identity only when verified.

## Alternatives Considered

- **Network isolation so only the router reaches the gateway.** Rejected: git and MCP clients reach the gateway directly from the runner by design (S14), and it would also change the topology. Signing leaves that path and records it as unauthenticated.
- **Per-runner tokens or mTLS.** Rejected: a new secret-distribution scheme the adopter would have to operate, and it moves the trust to a credential the runner holds.
- **Keep trusting the headers and only document it.** Rejected: any process on `agents` forges any user.
- **Normalize the path and forward the result.** Rejected: normalization differs between this gateway and the upstream; refusing ambiguous input removes the divergence.
- **A bare denylist plus more names.** Rejected: unknown credential headers keep arriving; only an allowlist closes the class.

## Open Decisions

- Whether the router should validate the end user (OIDC token) before signing. Decided by a follow-up spec once the runner and IdP wiring is chosen; this spec records, honestly, that the signature attests the router, not the end user.

## Risks

- ACCEPTED — a runner that calls the router can still choose its own `X-Forge-User`, and the router signs it. The audit then shows a router-attested claim, not an authenticated user; the field `identity: router` says exactly that. Closing it needs router-side authentication (Open Decisions).
- A runner holding a valid signed header could replay it for 300 s. Mitigation: it never sees router-to-gateway traffic; the window is short; the signature covers user and session.
- The method/path allowlist could block a legitimate client flow (a git or MCP verb). Mitigation: `git` and `mcp-catalog` allow the verbs their protocols need on the whole base path; the smoke covers the model route; a missing verb answers 403 and is a one-line config change.
- A secret mismatch between router and gateway records every identity as unauthenticated. Mitigation: it fails safe, and the smoke asserts the signed case.
- Header allowlist drops a header an upstream needs. Mitigation: the list covers what the models, git smart-HTTP and MCP clients send; extend by one line.
