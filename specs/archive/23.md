## Problem

Spec 20 (PR #21) renders dex's config with `sed` inside the dex service in `compose.yaml`. If `OMNIGENT_OIDC_CLIENT_ID` contains `&` or `|`, the substitution breaks. Spec 20's review found this and the runner reproduced it. Fix the rendering: escape the replacement, or render without `sed`, for example `envsubst` or a tiny template step. Add a smoke or unit case with such a value.

Member of holetz/forge epic 1 (follow-up of S37).

## Proposal

- dex's config renders correctly when `OMNIGENT_OIDC_CLIENT_ID` carries `&`, `|`, `\`, `"`, `$`, a backtick, a space, `#` or `:`: the client id dex serves is byte-for-byte the value set in `.env`.
- The rendering is a small POSIX `sh` script that escapes each value for `sed` before substituting it, so the same code runs in the dex container and in a unit test on the host.
- A newline or carriage return in the client id is refused with a clear message instead of producing a broken config.
- A test in the repository gate renders the template with those values and proves the result, and it fails against the old inline `sed`.

## Out of Scope

- Percent-encoding the client id in Omnigent's login redirect: that is Omnigent's code, not this repository's.
- `$` in the value being expanded by Compose's own `.env` interpolation (`$$` is the documented escape): a Compose rule, noted in the README, not changed here.
- Rendering `DEX_ISSUER`, `DEX_PORT` and `DEX_REDIRECT_URI` defensively: they are built from ports and fixed text, never free-form.
- A live `docker compose up` smoke with a metacharacter id: Omnigent receives the same id through its own env and its redirect encoding is outside this fix. The unit test and `compose config` are the proof.

## Design

**Decision: escape in a script, not `envsubst`.** The dex image is minimal (busybox `sh`, `sed`) with no `envsubst`; a script needs no new dependency, and being a file it can be run by a host test, which an inline `command:` cannot.

**Two escaping layers, in order.** (1) YAML: the template quotes the client id (`id: "@DEX_CLIENT_ID@"`), so `\` and `"` in the value are backslash-escaped first; `:`, `#` and spaces then need nothing. (2) sed: `\`, `&` and `|` (the delimiter) are backslash-escaped in the replacement. The order matters: YAML escaping first, then sed escaping of the result.

**Rule:** a value substituted into a sed replacement is escaped for the replacement and for the delimiter; free-form values are also escaped for the target format. A newline cannot be escaped portably in a one-line `sed` replacement, so it is refused.

**Binding contracts:** the dex service keeps `sh -c ... && exec dex serve /tmp/config.yaml`; the template remains `local/dex/config.yaml` mounted read-only; the image pin is untouched.

## Alternatives Considered

- **`envsubst`.** Absent from the dex image; adding it means a custom image or a pulled helper. Rejected.
- **Passing the client id to dex through its own env expansion (`secretEnv`-style).** dex expands `$VAR` only in specific fields, not `id`. Rejected as unverified.
- **A different `sed` delimiter.** Any delimiter can occur in the value. Rejected.

## Risks

- The script runs under busybox `sh` in the container but is tested under the host `sh`: a difference in `printf` or `sed` bracket handling could pass the test and fail live. Mitigation: only POSIX constructs, no bashisms; the test runs with `sh` (dash where available), and the Out of Scope note records that no live smoke was run.
- Quoting the id changes the template for existing users. Mitigation: a plain id renders to the same scalar value, and the smoke's `omnigent-smoke` case stays valid.
