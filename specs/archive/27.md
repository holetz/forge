## Problem

Spec 24 (PR #25) closed audit-identity spoofing between runner and gateway: the router signs `X-Forge-Identity` with HMAC-SHA256, using a secret shared only with the gateway. A residual risk was recorded as accepted. A runner that calls the router can still name any user, and the router signs whatever name it is given. The router should derive the identity from a validated OIDC token: the dex issuer locally, the adopter's provider by configuration. That means checking the signature against the issuer's JWKS, plus the audience, expiry and issuer. A request with no valid token is signed as `unauthenticated`, or refused, depending on the profile. Omnigent's session must carry that token, or a token exchanged for it, to the router; develop confirms how Omnigent forwards it.

Done when unit tests cover a valid token, a forged one, an expired one, a wrong audience and a missing token; `smoke-server.sh` proves the attested identity through the dex login; and the gate and CI are green. No CI workflow change and no new grant.

Member of holetz/forge epic 1 (follow-up of S39).

## Proposal

- Every place that implies the audit identity attests the user now states that it attests the router: the signed `X-Forge-Identity` proves the call came through the router, not who the user is.
- A short threat note (`docs/audit-identity.md`) says who can name whom, what the signature does and does not prove, and why the pilot accepts it.
- The upstream feature request lives as a draft at `docs/upstream/omnigent-forward-user-token.md`, ready for the human to file; nothing is filed.
- No behaviour changes: only prose, docstrings and comments are edited. This supersedes the OIDC-validation goal in `## Problem`, per the dated decision in `## Open Decisions`.

## Out of Scope

- JWKS/OIDC token validation in the router: Omnigent v0.19.1 forwards no per-user token, so there is nothing to validate; reopened when Omnigent ships a forwarding mechanism.
- Patching or forking Omnigent: breaks the thin-adaptation rule.
- Verifying Omnigent's HS256 session cookie at the router: needs the same upstream hook and hands the router a secret that mints any user's session.
- Filing the upstream issue: an outward action on a third-party repository, left to the human.
- Any change to `X-Forge-Identity` signing, to the gateway's verification, to smoke scripts, CI workflows or grants.
- `docs/server-sizing.md` and `docs/overlay-contract.md`: read, neither implies the identity attests the user; left untouched.

## Design

- **Decision (dated 2026-10-25, conductor):** accept S39's residual risk and document it. The `X-Forge-Identity` HMAC proves provenance (the router, holding the shared secret, vouched for the pair), not the user's identity: a runner that reaches the router can name any user and the router signs the name it is given.
- **Durable rule:** wording about the audit identity says "attests the router/provenance"; it never says it identifies, authenticates or verifies the user.
- **Threat note shape:** who can name whom (runner names any user to the router; the router signs it; the gateway records it as `router`-attested; a direct call to the gateway is `unauthenticated`), what the signature protects (forgery past the router), what it does not, why the pilot accepts it (single-tenant pilot behind the router, no user-level authorization built on the audit), and the reopen condition (Omnigent forwards a per-user token).
- **Upstream draft:** states the observed limits (one static key from the process environment; a session token minted by Omnigent and never sent to the model endpoint), asks for per-request headers or a hook on model calls carrying the validated user token, and offers the use case. It names versions and file paths of the public project only.
- **Contract:** router and gateway `sign_identity` stay unchanged in behaviour; only docstrings change.

## Alternatives Considered

- **JWKS validation at the router** — lost: no token reaches the router from Omnigent v0.19.1.
- **Fork or patch Omnigent** — lost: breaks the thin-adaptation rule.
- **Verify the Omnigent session cookie with a shared secret** — lost: needs the same upstream hook and gives the router a secret that mints any user's session.
- **Leave the wording as is** — lost: the docs imply the audit names the user, which the design does not guarantee.

## Discoveries

- Omnigent v0.19.1 cannot forward the caller's OIDC token to the model base URL: omnigent/inner/open_responses_sdk.py builds OpenAI(base_url=OPENAI_BASE_URL, api_key=OPENAI_API_KEY) from process env (one static key, no per-user or per-request header hook), and omnigent/server/routes/auth.py _validate_id_token validates the IdP id_token at callback then discards it; the session is an Omnigent-minted HS256 cookie JWT (omnigent/server/oidc.py mint_session_token, sub=email, signed with OMNIGENT_OIDC_COOKIE_SECRET), not a JWKS-verifiable token and never sent to the LLM endpoint.
