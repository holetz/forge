## Problem

Spec 24 (PR #25) closed audit-identity spoofing between runner and gateway: the router signs `X-Forge-Identity` with HMAC-SHA256, using a secret shared only with the gateway. A residual risk was recorded as accepted. A runner that calls the router can still name any user, and the router signs whatever name it is given. The router should derive the identity from a validated OIDC token: the dex issuer locally, the adopter's provider by configuration. That means checking the signature against the issuer's JWKS, plus the audience, expiry and issuer. A request with no valid token is signed as `unauthenticated`, or refused, depending on the profile. Omnigent's session must carry that token, or a token exchanged for it, to the router; develop confirms how Omnigent forwards it.

Done when unit tests cover a valid token, a forged one, an expired one, a wrong audience and a missing token; `smoke-server.sh` proves the attested identity through the dex login; and the gate and CI are green. No CI workflow change and no new grant.

Member of holetz/forge epic 1 (follow-up of S39).

## Open Decisions

- ~~**How the router learns the user's identity**~~ — **decided by the conductor on 2026-10-25**, under the human's delegation of medium-confidence decisions. Omnigent v0.19.1 cannot forward a per-user token (see Discoveries). The decision is option 4, plus a draft for upstream.
  - Accept S39's residual risk as documented: the signed `X-Forge-Identity` attests that the call came through the router, not who the user is.
  - Reword every place that implies the identity attests the user: README, `egress.py` docstring, `docs/server-sizing.md`, `docs/overlay.md` if it mentions it.
  - Add a short threat note: who can name whom, and why the pilot accepts it.
  - Write the upstream feature request as `docs/upstream/omnigent-forward-user-token.md`: per-request headers, or a hook on model calls that carries the validated user token. It is not filed. Opening an issue on a third-party repository is an outward action left to the human.
  - Rejected: patching or forking Omnigent (breaks the thin-adaptation rule), and verifying Omnigent's HS256 session cookie with a shared secret (needs the same upstream hook, and hands the router a secret that mints any user's session).
  - Reopen JWKS validation at the router when Omnigent ships a forwarding mechanism.

## Discoveries

- Omnigent v0.19.1 cannot forward the caller's OIDC token to the model base URL: omnigent/inner/open_responses_sdk.py builds OpenAI(base_url=OPENAI_BASE_URL, api_key=OPENAI_API_KEY) from process env (one static key, no per-user or per-request header hook), and omnigent/server/routes/auth.py _validate_id_token validates the IdP id_token at callback then discards it; the session is an Omnigent-minted HS256 cookie JWT (omnigent/server/oidc.py mint_session_token, sub=email, signed with OMNIGENT_OIDC_COOKIE_SECRET), not a JWKS-verifiable token and never sent to the LLM endpoint. Read from the v0.19.1 source on GitHub; no container run.
