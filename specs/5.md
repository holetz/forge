## Problem

An adopter must configure identity provider, approved endpoints, policy parameters, role agents and catalog connectors without forking the open stack or leaking its own vocabulary into it. Define and document the overlay contract — what a private distribution overrides and how — with a synthetic example overlay and a leak gate in CI.

Member S15 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A document, `docs/overlay-contract.md`, states what a private distribution may override in forge and how: the identity provider, the model and tool endpoints, the egress allowlist, the MCP catalog entries, the policy parameters and the role agents. It also states what an overlay may never do.
- A private distribution is a directory kept outside forge that forge reads and never copies into itself; it is applied with extra `-f` and `--env-file` arguments, so forge's own files are never edited.
- `overlay/example/` is a complete synthetic overlay (a fictional "Example Corp") that exercises every override surface.
- `scripts/overlay-check.py <dir>` validates any overlay against the contract by calling forge's own egress and registry loaders, so the contract cannot drift from the code.
- `scripts/leak-overlay.sh <dir>` is the overlay leak scan: the generic leak patterns, plus a rule that every host, email and secret in the scanned directory is synthetic. `scripts/verify_repo.sh` runs it on `overlay/example/`, so CI (which already runs that file) refuses an overlay that carries a real-looking host, email or credential, with no change to the workflow files.
- Both new scripts are proved by tests that build throwaway overlays at run time.

## Out of Scope

- Editing `.github/workflows/*`: CI already runs `scripts/verify_repo.sh`, so the scan rides on it. If that turns out insufficient, the spec stops as needs-human rather than editing a workflow.
- Consuming the policy and agent slots: the policy pack (S16) and the role agents (S12) own that. This spec reserves the slots and checks their shape only.
- The private distribution itself, its real values and its denylist: none of it is written here, and the real denylist stays outside the repository.
- A live smoke of the stack with the example overlay: the example points at the local stub and a fictional identity provider, and `docker compose config` proves it composes without pulling an image.
- Changing `compose.yaml`, `compose.server.yaml` or `.env.example`.

## Design

**An overlay is a directory, applied by arguments.** `docker compose --env-file .env.example --env-file <overlay>/overlay.env -f compose.yaml [-f compose.server.yaml] -f <overlay>/compose.overlay.yaml up`. Later `--env-file` wins, later `-f` merges over earlier. forge never reads the overlay's location from a tracked file, so the open tree names no private path.

**The override surfaces are closed and listed.**

| Surface | File in the overlay | How it takes effect |
|---|---|---|
| Identity provider | `compose.overlay.yaml` + `OVERLAY_OIDC_*` in `overlay.env` | the overlay points `OMNIGENT_OIDC_ISSUER` at the corporate issuer and drops the `dex` dependency with `depends_on: !override`; client secret and cookie secret stay variables supplied from the shell |
| Model endpoints | `overlay.env` | `FORGE_*` and `EGRESS_MODELS_*` base URLs and models (already variables) |
| Egress allowlist | `upstreams.json`, mounted at `/overlay` and selected by `EGRESS_UPSTREAMS_FILE` | a full replacement; must keep `models-default` and `models-escalation` and satisfy the gateway's own loader (every upstream declares `allow`; fail closed) |
| Catalog and tool connectors | `registry.json` + the upstream it names | checked with the registry's own loader; every role it lists is declared by a role agent |
| Policy parameters | `policy/params.json` | reserved slot, consumed by the policy pack (S16); shape checked only |
| Role agents | `agents/*.json` | reserved slot, consumed by the role agents (S12); each declares `name` and `description` |

**The contract is enforced by calling the code, not by restating it.** `overlay-check.py` imports `load_upstreams` from `server/egress/egress.py` and `load_registry` from `server/mcp/registry.py` (stdlib, no install). Its other rules: `overlay.json` declares `contract: 1` and a `name`; `overlay.env` may set only a variable named in `.env.example` (commented placeholders included), one an overlay upstream names in `base_url_env`/`token_env`, or an `OVERLAY_`-prefixed one; a variable ending `_TOKEN`, `_SECRET` or `_PASSWORD` must be empty or a placeholder (`<...>`, `change-me...`, `stub-token`), because overlay files are committed and credentials come from the shell or a secret store.

**What an overlay may never do** (documented, and checked where a file can show it): hold a credential value; open a route out of the gateway (an upstream without `allow`); give an agent a real URL (registry entries name an upstream, never a host); replace forge's files. The compose override is validated by `docker compose config`, not by a parser of our own.

**The leak scan has two directions.** (a) `leak-overlay.sh` over an overlay: the six generic patterns of `leak-generic.sh` (same list, same duty to keep aligned by hand, said in its header), plus the synthetic rule: every `http(s)` URL host must be a reserved name (`example.com|org|net`, `*.example`, `*.test`, `*.invalid`, `localhost`, `127.0.0.1`), a dotless compose service name, or a `<placeholder>`/`${VAR}`; every email must be at an `example.*` domain. It scans files with `grep -r`, tracked or not, so it works on a private overlay before any commit. forge's gate runs it on `overlay/example/`, where the synthetic rule is the guarantee that the example never carries a real host. (b) The private organization's own vocabulary is still the hooks' job (`cq security leak` and the denylist outside the repo); the contract tells an adopter to run them against any change it sends back to forge. Output names `file:line` and the rule, never the matched text; a `grep` error is exit 2, not clean.

**The gate stays Docker-free for the scan.** Both scripts need only bash, grep and python3. The compose check for the example runs only where docker exists, like the two existing compose checks, and `config` pulls nothing.

**Binding contracts:** `.github/workflows/` untouched; `compose.yaml`, `compose.server.yaml` and `.env.example` untouched; every example value is synthetic (fictional "Example Corp", reserved domains, `change-me`/empty secrets); tests assemble their fake leaks at run time so no tracked file matches a pattern or trips gitleaks.

| File | Relation | What breaks if it changes |
|---|---|---|
| `server/egress/egress.py` (`load_upstreams`) | imported by `overlay-check.py` | a signature change breaks the checker; the checker's test catches it |
| `server/mcp/registry.py` (`load_registry`) | imported by `overlay-check.py` | same |
| `server/egress/upstreams.json`, `server/mcp/registry.json` | the base the overlay replaces | the checker requires the overlay to keep `models-default` and `models-escalation`; the router's paths depend on them |
| `.env.example` | the list of variables an overlay may set | a renamed variable makes the example overlay fail the check, on purpose |
| `compose.yaml`, `compose.server.yaml` | merged under the overlay | the example override names `omnigent`, `dex`, `egress`, `mcp-registry`; renaming one breaks `config -q` |
| `scripts/leak-generic.sh` | pattern list mirrored by `leak-overlay.sh` | aligned by hand, said in both headers |
| `scripts/verify_repo.sh` | runs the new steps; CI runs it | a slow or Docker-dependent step would slow CI |

## Alternatives Considered

- **A templating tool (kustomize, helm) for overlays:** rejected; the stack is plain compose, and compose already merges files and env files in order.
- **Fork per adopter:** the problem this spec exists to remove; rejected.
- **Add a CI job for the overlay scan:** rejected by the human's instruction; the gate file already runs in CI.
- **A YAML schema validator for `compose.overlay.yaml`:** rejected; no YAML library in the stdlib, and `docker compose config` is the authority on compose.

## Open Decisions

- **Whether the policy and role-agent slots keep these file shapes:** decided when S16 and S12 land their consumers; until then they are reserved and checked for well-formedness only.
- **A published contract version bump policy:** `contract: 1` now; the rule for a `2` is decided with the first breaking change, by the owner.

## Risks

- **The synthetic-host rule rejects a legitimate placeholder:** mitigated by the explicit allowed forms (`<placeholder>`, `${VAR}`, reserved names, dotless service names); a false positive is fixed in the example, never by weakening a pattern.
- **Contract drift from `.env.example`:** the checker reads `.env.example` at run time, so the allowed set follows the file.
- **The generic pattern list in `leak-overlay.sh` drifts from `leak-generic.sh`:** ACCEPTED — the same hand alignment forge already accepts for `leak-generic.sh` against `cq`; both headers say so.
- **The scan sees only this directory:** an adopter's real vocabulary is not caught by generic patterns; the contract names the hooks and the outside denylist as the second direction.
- **Compose `!override` needs Compose 2.24 or later:** the repository already uses it in `compose.server.yaml`.
