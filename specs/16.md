## Problem

Spec 14 re-graded the 36 saved H1 cases with Flash 1017 as the grader: on the 98 assertions it graded it agrees 100% with Opus 5.5 (0 risky verdicts), but 6 cases ended `finish: length` at the 8,000-token completion cap because Flash spends its output on reasoning, leaving 22 assertions `unknown` and overall agreement at 81.7% (`spikes/h1/REGRADE.md`). Re-grade only those six cases (push-request-declines on the opus and sonnet arms, staged-change-committed on the flash arm, new-term-added and existing-term-refined on the opus arm, capture-happy-path on the sonnet arm) with a 16,000-token completion cap, one call at a time, through the existing `spikes/h1/regrade.py`, and update REGRADE.md with the new agreement and the recommendation on Flash as the default grader. The human allowed this run on 2026-10-24 with a cap of US$ 0.25 for it (the epic's Databricks total is capped at US$ 10, ≈ US$ 6.28 spent); no agent arm runs again.

Member of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- The six truncated cases each have one new Flash grade made at a 16,000-token completion cap, stored apart from the recorded results of the other 30.
- `regrade.py` gains a retry mode with its own output folder, ledger, token cap and spend cap (US$ 0.25) that refuses any call whose worst-case price crosses it; the default run and the recorded files stay as they were.
- `compare` can overlay the retried grades, so agreement is reported overall, per arm and per suite on the merged set.
- `spikes/h1/REGRADE.md` states the new agreement, any case still truncated as `unknown`, the measured tokens and US$, and an updated recommendation on Flash as the default grader.

## Out of Scope

- Running any agent arm: only grading calls are made.
- Retrying a case that is still truncated at 16,000: it stays `unknown`, because a second retry would break the spend limit the owner set.
- Editing the recorded results of the other 30 cases or the original 8,000-token files: the run is additive.
- Changing the grader prompt, the model or the evidence rule: that would make the six incomparable with the 30.
- Making Flash the default grader in the eval runner: the spec only recommends.

## Validation

- `python3 spikes/h1/regrade.py plan` still exits 0 with 36 jobs and no network call.
- `python3 spikes/h1/regrade.py run --retry-truncated --limit 1` makes one call at max_tokens 16000 and appends to the retry ledger only; repeated, it never selects a job that already has a retry file.
- The retry ledger total stays at or below US$ 0.25, and a call whose worst-case price would cross it is refused before it is made (exit 1).
- `python3 spikes/h1/regrade.py compare --md` reports the merged set, and the 30 untouched case files are byte-identical (`git status` shows nothing changed under `spikes/h1/results/regrade/`).
- The leak grep for tokens, workspace hosts, `/home/` and emails finds nothing in the touched files and the new results.
- Commit hooks run without `--no-verify`.

## Design

- The retry is a mode of the existing driver (`--retry-truncated`), not a new script, so the prompt, material limit and evidence rule are shared and the six stay comparable with the 30.
- Retry files live in `results/regrade-16k/`, with their own `ledger.json`; the original `results/regrade/` is read-only to this mode. Rule: a retried grade overlays the original in `compare` only when the retry finished with a reason other than `length`; a retry that is still truncated is recorded but the case stays `unknown`.
- The job list for the retry is the set whose original file has `finish == "length"` (read from disk, not hard-coded) and which has no retry file yet; this yields the six and makes a second invocation a no-op.
- The cap is code: `RETRY_CAP_USD = 0.25` and `RETRY_MAX_TOKENS = 16000`; `worst_case` takes the token cap as a parameter. The cap check uses the retry ledger only, and a refused call exits 1 before any request.
- Pricing: the existing Flash prices in `prices.json`; reasoning tokens count as output.

## Alternatives Considered

- Editing `MAX_TOKENS` and rerunning all 36: rejected, it spends about US$ 0.27 and rewrites the recorded results.
- A separate retry script: rejected, it would duplicate the prompt and evidence rule and risk drift.
- Asking for shorter reasoning instead of a larger cap: rejected, changes the prompt, so the six would not be comparable.

## Open Decisions

- none — the cap, the token limit, the six cases and the no-second-retry rule were fixed by the owner in the Problem.

## Risks

- A case still truncated at 16,000: ACCEPTED — it stays `unknown` and the report says so; the recommendation then rests on the remaining coverage.
- The six calls cost more than estimated: the pre-call worst-case check against US$ 0.25 refuses the call, and the partial result is reported.
- A token or host leaking into a committed file: both travel by variable name only, and the leak grep plus the commit hooks run before the commit.
