## Problem

`compose.yaml:96` still pins the Omnigent server at v0.19.1, while a local server ran v0.20.0
(`ghcr.io/omnigent-ai/omnigent-server:v0.20.0@sha256:2a98e55fb9297e37c9a28e32cf11858a821fa4953dce9453b9ba59305a437ed5`)
on 2026-10-28 through a temporary override kept outside the repository. Upgrading is a manual
command today, and the v0.20.0 start migrated the Postgres schema automatically
(`nf12ab34cd56` → `b2e4f6a8c013`), so rolling back the image without restoring the database is not
viable. The same run proved that recreating only the `omnigent` container (`--no-deps`) keeps a
live session: the runner reconnected and the server logged `Runner recovery completed ... after 0.1s`.

## Proposal

The Omnigent version changes through the project's deploy (the `current`/`previous`/`backups`
release flow from spec 30), never by a manual command:

1. Pin v0.20.0 with its digest in `compose.yaml` and prove it with `scripts/smoke-local.sh`, as
   `docs/policy-pack.md:66` requires for every pin bump.
2. The deploy pulls the image first, takes a `pg_dump` into `backups/` before the migration,
   recreates only the `omnigent` service, waits for healthy and checks that the runners reconnected.
3. Rollback restores that dump and points `current` back at `previous`.
4. Version bumps arrive as automatic PRs for the compose images, with the gate and the smoke in CI.

## Out of Scope

- Hiding the native harness agents (Claude Code, Codex, …) from the web UI: v0.20.0 seeds them
  unconditionally and exposes no setting for it.
- Listing models in the OpenCode model picker: the v0.20.0 host answers `model options are
  unsupported` for every harness but the Claude ones.

## Validation

- `bash scripts/smoke-local.sh` passes with v0.20.0 pinned in `compose.yaml`.
- A deploy upgrade on the approved host leaves a `pg_dump` in `backups/` taken before the
  migration, and a session open during the upgrade survives with its runner reconnected.
- A rollback restores the pre-migration dump and the previous release serves healthy.
- A version bump of the server image opens a PR on its own, and that PR runs the gate and the smoke.

## Design

- The pin stays: the policy pack runs inside the server (`PYTHONPATH=/policy`) and depends on its
  internals, so each version must pass the smoke before it reaches a host.
- Sessions survive a server restart because their state lives in Postgres and the agents run in
  the runners on each user's machine; the container is only the hub they reconnect to.
- Upgrade order: the server first, then the CLIs; `omnigent upgrade` on a client already waits for
  in-flight sessions by default.

## Alternatives Considered

- Auto-update inside the container (Watchtower, or an unpinned tag): dropped — it bypasses the pin
  and the smoke, and it restarts the server at an arbitrary moment, possibly mid-turn.
- Old and new servers side by side (blue/green): dropped — after the schema migration the old
  version cannot run on the same database, and the gain is a few seconds.

## Open Decisions

- Dependabot or Renovate for the compose image bumps.
- Whether a turn streaming during the restart resumes or must be resent; the smoke must prove it,
  and if it is lost the upgrade waits for in-flight turns before recreating the container.
- Whether a proxy with retry on connection errors in front of the server hides the restart window
  from the CLI and the web UI.
- Whether the smoke must also prove that a runner one version behind connects to the new server.

## Risks

- The schema migration is one-way: an upgrade without its pre-migration dump has no rollback.
- A new server version can break the policy pack loading or silently disable it.
