## Problem

Moving coding agents from individual subscriptions to API access gives a team central audit, routing by data classification and a path for people who do not use a terminal, but frontier-model token prices make that move unaffordable at team scale. Three recent facts make an alternative plausible:

- **A cheap open model.** DeepSeek V4.1 Flash 1017 (released 2026-10-17, open weights under MIT, 1M-token context, US$ 0.30 input / 0.006 cached / 1.20 output per 1M tokens on the official API) is served pay-per-token by Azure Databricks itself, without going through the vendor's own API.
- **An open meta-harness.** Omnigent (published by Databricks in June 2026 under Apache 2.0) runs Claude Code, Codex, OpenCode, Pi and custom agents behind one API, with policies, cost budgets, sandbox and shareable sessions; it starts with `docker compose up` and accepts any OpenAI- or Anthropic-compatible endpoint.
- **Mature open assets.** quenching already governs specs, git and knowledge; bricksmith is already the open data framework.

No open, self-hostable package ties these together with guardrails enforced by the platform (never only by prompt) and with institutional context — specs, conventions and data-catalog metadata — handed to the model.

## Proposal

Deliver a self-hosted environment around Omnigent, with its own model routing and MCP servers, that becomes a data team's main AI-assisted development environment for its monorepo — and publish every generic part as open source. Seven new open projects plus one private distribution, on top of quenching and bricksmith:

| # | Project | Scope | Depends on | Out of its scope |
|---|---|---|---|---|
| 1 | **forge** — platform stack | docker compose with Omnigent, a model router over Unity Gateway, OIDC, Postgres, egress proxy, observability and an MCP registry; local and server profiles | Omnigent | any adopter's rules |

This epic orchestrates the whole delivery: it is decomposed into member specs — slices of each project above plus one spike per hypothesis H1–H6 (`## Design`) — sequenced by gates, not dates: phase 0 (discovery spikes and local compose) → pilot → expansion. Nothing goes to pilot before a hosting option is approved; nothing expands before the cheap model proves its quality (H1, which runs first). Member specs live in this store and name the repository that carries the work.

Phase 0 next steps recorded by the discovery: take the guardrails and hosting options to compliance and security; interview one person per role with the persona script; run a first cut of the quenching evals with the Flash model (H1), still outside Omnigent; bring up the Omnigent compose locally with the gateway and a test endpoint; register the discovery as this epic, one spike per hypothesis.

## Out of Scope

- Training or fine-tuning own models.
- Replacing Databricks, Genie or Power BI — the environment orchestrates, it does not substitute.
- Replicating in the catalog what Unity Catalog already serves: the agent reaches Databricks directly with the person's own identity, and hallmark only adds the table/column ↔ source-code link.
- Sandboxes on Windows workstations: containers are developed on Linux and the compose runs on a Linux VM inside the adopter's private network; workstations only access it through the web, VS Code or a remote terminal.
- Any adopter's code, vocabulary or data in the open projects — that belongs to the private distribution (#8), and a leak gate checks it in CI, the same boundary rule as bricksmith.

## Design

### Architecture

The compose concentrates the control points: a person enters through Omnigent, the agent runs in containers on a Linux VM inside the adopter's private network, and every egress to a model, Databricks or git goes through the gateway or the proxy, where it is recorded. hallmark answers from a local index; only the job that refreshes the index talks to Unity Catalog and the other sources, through the proxy. The server is sized for 30 concurrent sessions.

The model gateway is Databricks Unity Gateway, since every model comes from Azure Databricks: per-group permission, per-user limits, budget with blocking and usage recorded in `system.ai_gateway.usage`. The compose router only routes by task.

**Harness.** OpenCode is the default harness: open, model-agnostic, and runs both on Omnigent and on Unity Gateway (`ug opencode`), so the Flash model needs no adaptation. Claude Code is used only for sessions escalated to Opus 5.5, where it runs with the model it was built for. Pi is the alternative if OpenCode does poorly in H1.

### Guardrails

Every control lives in a layer the agent cannot bypass by writing code. Prompt and prose guide; gateway, sandbox, proxy and data permissions enforce. quenching declares it is not a security boundary, so guardrails must live in the platform.

| Layer | Control | Enforced at | Omnigent status |
|---|---|---|---|
| Identity | corporate SSO; every session belongs to a person | Omnigent server via OIDC | supported (`OMNIGENT_OIDC_ISSUER`) |
| Roles | per-role permissions | server and agent policies | policies at three levels: server, agent, session |
| Model | approved endpoints only; routing by data classification | Unity Gateway; subscription credentials off | OpenAI/Anthropic-compatible gateway supported |
| Cost | budget per session, person and team | `cost_budget` policy + gateway limits | `cost_budget` with cap and warnings |
| Execution | OS sandbox; human approval before push, deploy and sensitive commands | Linux sandbox (bubblewrap) and policies | supported; no isolation on Windows |
| Network and secrets | egress allowlist; token injected only at the proxy | egress proxy | described in the announcement; validate in a spike |
| Data | agent uses the person's Databricks identity; read-only by default; PII masked in UC | Unity Catalog | outside Omnigent |
| Audit | who asked what, of which model, at what cost, with what result | gateway + telemetry + session log | audit log undocumented: a gap |
| Output | secret and PII scanning on commit and response | policy + pre-commit hook | to build (#4) |

### Model routing

| Model (endpoint) | Proposed role | Input US$/1M | Cache US$/1M | Output US$/1M | Note |
|---|---|---|---|---|---|
| DeepSeek V4.1 Flash 1017, `databricks-deepseek-v4-1-flash-1017` | default for every role | 0.30 | 0.03 | 1.20 | replaces V4.1 Flash on 2026-11-19 |
| Claude Opus 5.5, `databricks-claude-opus-5-5` | escalation: security, architecture, repeated failure | 4.00 | 0.20 | 20.00 | new input pays the cache write, US$ 5.00; +10% with regional processing |
| Claude Sonnet 5.5, `databricks-claude-sonnet-5-5` | optional middle step | 2.00 | 0.20 | 10.00 | text only |
| Claude Haiku 5.5, `databricks-claude-haiku-5-5` | cheap alternative, tested in H1 | 0.10 | 0.01 | 0.50 | short context; long context 0.50 / 0.05 / 2.50 |
| OpenJev (Qwen3.5 4B), `databricks-openjev-qwen35-4b` | classify the task for routing; judge answers | — | — | — | returns probabilities, no text; price unpublished |
| GLM 5.3 Flash, `databricks-glm-5-3-flash` | open fallback if Flash fails H1 | 0.15 | 0.03 | 0.50 | 1M-token context |

Prices are Databricks DBU list prices converted at US$ 0.07 per DBU (US regions; the workspace region's rate comes from `system.billing.list_prices`).

- **Default:** Flash for everything that does not need a frontier model.
- **Escalation:** Opus 5.5 only for marked tasks (security review, architecture, repeated failure) on coding profiles, targeting at most 2% of tokens, with its own budget.
- **Classification:** OpenJev decides when to escalate and judges answers as an LLM-as-a-judge policy in Unity Gateway, without generating output tokens.
- **By tier:** light users stay on Flash, or on Haiku 5.5 if it passes H1.
- **Control:** `EXECUTE` per group on each model, per-user token limit, team budget with blocking in Unity Gateway, individual alert above a monthly threshold.

Volume model: using 100% of a Claude Max 5x subscription is roughly 7.3 billion tokens per month in SemiAnalysis's estimated agentic mix (0.4% fresh input, 96.6% cache read, 2.6% cache write, 0.3% output). Usage tiers: intense (~70% of that limit, ~5.0B tokens/person/month), medium (~20%, ~1.5B), light (web chat and lookup, ~0.3B). The intense tier carries about three quarters of the cost, so that is where escalation needs its own budget. The pilot measures real usage with `ccusage`.

### Personas

Roles fall into three usage modes — writing code in the monorepo, querying and analysing data, managing the work — and each mode calls for a pre-configured agent, not a different tool. The web UI is the primary interface for everyone; VS Code is for git, notebooks and files; the terminal is for heavy users. Roles: model-monitoring data scientist, AI engineer, data engineer, MLOps engineer, data scientist, data analyst, BI analyst, PO, agile coach, coordinator, platform developer. The jobs per role are hypotheses to confirm in interviews.

## Alternatives Considered

- **Frontier model only.** Several times the cost target; subscriptions hide the gap — per SemiAnalysis a Max plan delivers 12 to 63 times its price in API value — so the migration only closes with a cheap default model.
- **Managed Omnigent on Databricks.** In Beta, documented for AWS, no Python policies, no own key in the Sandbox: a reference, not a base, since the chosen path is self-hosting on a VM in the private network.
- **Running the compose directly on Databricks.** Dropped: costs more, gains little.
- **Provisioned throughput for Flash.** The 50-unit minimum only breaks even with pay-per-token around 160–175 billion tokens per month, about five times the estimated team volume.
- **tempering as `quenching/mcp` in a single monorepo.** The discovery left both open; the standalone `holetz/tempering` repository was created, so folding it back is a later decision, not the default.

## Open Decisions

- **Catalog engine, build vs adopt** (spike): build hallmark on a metadata generator like the one the reference monorepo already has, or index an existing catalog such as OpenMetadata or DataHub.
- **H1 quality threshold** against the Claude baseline, and whether Haiku 5.5 replaces Flash for the light tier.
- **Omnigent upgrade policy:** Omnigent is alpha, so the platform needs a rule for how it is upgraded and who approves each version.
- **Persona jobs** are hypotheses until the interviews confirm them.
- **Member decomposition:** the slices of each project and their dependencies are not yet captured as member specs — the develop pass does it.

## Risks

- **Omnigent in alpha:** API and configuration format may change — pin the version and keep a thin adaptation layer.
- **Managed version in Beta:** documented for AWS only; used as a reference, not a base.
- **OpenCode + Flash unmeasured:** if H1 lands below the baseline, Pi is the next candidate and routing turns hybrid.
- **Windows workstations have no sandbox:** agents run in containers on a Linux VM; people access through web, VS Code or a remote terminal.
- **Audit gap:** Omnigent's audit log is undocumented; the gateway and telemetry must cover it.
- **Leakage into the open projects:** a leak gate in each project's CI, the same rule as bricksmith.
- **Scope vs capacity:** seven new projects plus the quenching adaptation depend on a single maintainer in spare time; the roadmap sequences by risk.
