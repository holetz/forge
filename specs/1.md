## Problem

Moving coding agents from individual subscriptions to API access gives a team central audit, routing by data classification and a path for people who do not use a terminal, but frontier-model token prices make that move unaffordable at team scale. Three recent facts make an alternative plausible:

- **A cheap open model.** DeepSeek V4.1 Flash 1017 (released 2026-10-17, open weights under MIT, 1M-token context, US$ 0.30 input / 0.006 cached / 1.20 output per 1M tokens on the official API) is served pay-per-token by Azure Databricks itself, without going through the vendor's own API.
- **An open meta-harness.** Omnigent (published by Databricks in June 2026 under Apache 2.0) runs Claude Code, Codex, OpenCode, Pi and custom agents behind one API, with policies, cost budgets, sandbox and shareable sessions; it starts with `docker compose up` and accepts any OpenAI- or Anthropic-compatible endpoint.
- **Mature open assets.** quenching already governs specs, git and knowledge; bricksmith is already the open data framework.

No open, self-hostable package ties these together with guardrails enforced by the platform (never only by prompt) and with institutional context — specs, conventions and data-catalog metadata — handed to the model.

## Proposal

Deliver a self-hosted environment around Omnigent, with its own model routing and MCP servers, that becomes a data team's main AI-assisted development environment for its monorepo — and publish every generic part as open source. Two new open projects plus one private distribution, on top of quenching and bricksmith; quenching grows to carry the specs service (human's direction, 2026-10-24):

| # | Project | Scope | Depends on | Out of its scope |
|---|---|---|---|---|
| 1 | **forge** — platform stack, policies and cost | docker compose with Omnigent, a model router over Unity Gateway, OIDC, Postgres, egress proxy, observability and an MCP registry; local and server profiles; the generic Omnigent policy pack (approval before push and deploy, budgets, egress blocking, secret and PII detection on output); cost per person, team, session and project summing LLM (gateway log), Databricks and Genie agents (`system.billing.usage`), spend against budget and alerts over MCP for the coordinator's panel | Omnigent, quenching | any adopter's rules, values and lists |

## Out of Scope

- Training or fine-tuning own models.
- Replacing Databricks, Genie or Power BI — the environment orchestrates, it does not substitute.
- Replicating in the catalog what Unity Catalog already serves: the agent reaches Databricks directly with the person's own identity, and hallmark only adds the table/column ↔ source-code link.
- Sandboxes on Windows workstations: containers are developed on Linux and the compose runs on a Linux VM inside the adopter's private network; workstations only access it through the web, VS Code or a remote terminal. Running quenching itself on Windows without administrator rights is in scope (S30).
- **quenching never requires forge to work.** The specs service runs over stdio on a workstation with no infrastructure; forge depends on quenching, never the reverse.
- GitHub Projects: the open projects' specs use GitHub Issues only, for now.
- New features in quenching's git spec backend: from 2026-10-24 it only waits for its retirement (S33).
- Any adopter's code, vocabulary or data in the open projects — that belongs to the private distribution (#3), and a leak gate checks it in CI, the same boundary rule as bricksmith.

## Design

### Architecture

The compose concentrates the control points: a person enters through Omnigent, the agent runs in containers on a Linux VM inside the adopter's private network, and every egress to a model, Databricks or git goes through the gateway or the proxy, where it is recorded. hallmark answers from a local index; only the job that refreshes the index talks to Unity Catalog and the other sources, through the proxy. The server is sized for 30 concurrent sessions.

The model gateway is Databricks Unity Gateway, since every model comes from Azure Databricks: per-group permission, per-user limits, budget with blocking and usage recorded in `system.ai_gateway.usage`. The compose router only routes by task.

**Spec store.** Specs live in a tracker, not on a git branch: Azure Boards for the adopter, GitHub Issues for the open projects. In Azure Boards the whole spec is the work item's `System.Description` in Markdown (ceiling 1,048,576 characters; the largest quenching spec is 129 KB) and its history is the work item's revisions; in GitHub Issues it is the issue body, and `after:` is the native "blocked by / blocking" dependency (GA since August 2025, with REST and webhooks). The code repository keeps only code. The flow is one path:

```
quenching commands and agents ⇄ quenching specs service (MCP | cq) ⇄ store adapters (Azure Boards | GitHub Issues)
```

The specs service is one rules core with two ports in the same process: the MCP server, which agents use, and the `cq` CLI, which stays for scripts, CI and hooks. The same server runs over **stdio, locally**, with no infrastructure, or over **HTTP on forge**, where it is the single writer with one central credential, receives webhooks and service hooks, and keeps a shared cache. quenching's management interface — boards and a Gantt over the schedule quenching derives (S5), starting from `cq specs serve` — reads from that cache, and every edit made in it or by an agent is written back through the adapter, so the tracker stays the one source of truth. Boards keeps its native views (backlog, Delivery Plans over `start`, `target` and predecessor links). Read latency is taken as comparable to the git store by the human's direction (2026-10-24). This is the market's pattern: Azure Boards hands a work item's Description and comments to the GitHub Copilot coding agent, which opens a draft PR linked back to it, and Microsoft's Azure DevOps MCP server exposes work items, PRs and builds to any agent.

**Harness.** OpenCode is the default harness: open, model-agnostic, and runs both on Omnigent and on Unity Gateway (`ug opencode`), so the Flash model needs no adaptation. Claude Code is used only for sessions escalated to Opus 5.5, where it runs with the model it was built for. Pi is the alternative if OpenCode does poorly in H1.

### Store backends

The sequence quenching's backends follow (human's direction, 2026-10-24):

1. `azure` and `github` move behind the specs service — S4 (read port), S29 (predecessor links), S31 (GitHub Issues adapter), S32 (store location in the repository, credential outside it).
2. `memory` stays, for the tests.
3. `git` gets no new feature and is **retired last** (S33): after the tracker adapters reach parity and quenching's own store has moved to Azure DevOps (`https://dev.azure.com/holetz/quenching`, a personal organization, free up to five users) through `cq specs migrate --to azure` (S28). Until S32, quenching reaches that organization by isolating `az` per project with `AZURE_CONFIG_DIR` in `.claude/settings.local.json`.

### Guardrails

Every control lives in a layer the agent cannot bypass by writing code. Prompt and prose guide; gateway, sandbox, proxy and data permissions enforce. quenching declares it is not a security boundary, so guardrails must live in the platform.

| Layer | Control | Enforced at | Omnigent status |
|---|---|---|---|
| Identity | corporate SSO; every session belongs to a person | Omnigent server via OIDC | supported (`OMNIGENT_OIDC_ISSUER`) |
| Roles | per-role permissions | server and agent policies | policies at three levels: server, agent, session |
| Model | approved endpoints only; routing by data classification | Unity Gateway; subscription credentials off | OpenAI/Anthropic-compatible gateway supported |
| Cost | budget per session, person and team | `cost_budget` policy + gateway limits | `cost_budget` with cap and warnings |
| Execution | OS sandbox; human approval before push, deploy and sensitive commands | Linux sandbox (bubblewrap) and policies | supported; no isolation on Windows |
| Network and secrets | egress allowlist; token injected only at the proxy | egress proxy | described in the announcement; validate in a spike |
| Data | agent uses the person's Databricks identity; read-only by default; PII masked in UC | Unity Catalog | outside Omnigent |
| Audit | who asked what, of which model, at what cost, with what result | gateway + telemetry + session log | audit log undocumented: a gap |
| Output | secret and PII scanning on commit and response | policy + pre-commit hook | to build (forge policy pack, S16) |

### Model routing

| Model (endpoint) | Proposed role | Input US$/1M | Cache US$/1M | Output US$/1M | Note |
|---|---|---|---|---|---|
| DeepSeek V4.1 Flash 1017, `databricks-deepseek-v4-1-flash-1017` | default for every role | 0.30 | 0.03 | 1.20 | replaces V4.1 Flash on 2026-11-19 |
| Claude Opus 5.5, `databricks-claude-opus-5-5` | escalation: security, architecture, repeated failure | 4.00 | 0.20 | 20.00 | new input pays the cache write, US$ 5.00; +10% with regional processing |
| Claude Sonnet 5.5, `databricks-claude-sonnet-5-5` | optional middle step | 2.00 | 0.20 | 10.00 | text only |
| Claude Haiku 5.5, `databricks-claude-haiku-5-5` | cheap alternative, tested in H1 | 0.10 | 0.01 | 0.50 | short context; long context 0.50 / 0.05 / 2.50 |
| OpenJev (Qwen3.5 4B), `databricks-openjev-qwen35-4b` | classify the task for routing; judge answers | — | — | — | returns probabilities, no text; price unpublished |
| GLM 5.3 Flash, `databricks-glm-5-3-flash` | open fallback if Flash fails H1 | 0.15 | 0.03 | 0.50 | 1M-token context |

Prices are Databricks DBU list prices converted at US$ 0.07 per DBU (US regions; the workspace region's rate comes from `system.billing.list_prices`).

- **Default:** Flash for everything that does not need a frontier model.
- **Escalation:** Opus 5.5 only for marked tasks (security review, architecture, repeated failure) on coding profiles, targeting at most 2% of tokens, with its own budget.
- **Classification:** OpenJev decides when to escalate and judges answers as an LLM-as-a-judge policy in Unity Gateway, without generating output tokens.
- **By tier:** light users stay on Flash, or on Haiku 5.5 if it passes H1.
- **Control:** `EXECUTE` per group on each model, per-user token limit, team budget with blocking in Unity Gateway, individual alert above a monthly threshold.

Volume model: using 100% of a Claude Max 5x subscription is roughly 7.3 billion tokens per month in SemiAnalysis's estimated agentic mix (0.4% fresh input, 96.6% cache read, 2.6% cache write, 0.3% output). Usage tiers: intense (~70% of that limit, ~5.0B tokens/person/month), medium (~20%, ~1.5B), light (web chat and lookup, ~0.3B). The intense tier carries about three quarters of the cost, so that is where escalation needs its own budget. The pilot measures real usage with `ccusage`.

### Personas

Roles fall into three usage modes — writing code in the monorepo, querying and analysing data, managing the work — and each mode calls for a pre-configured agent, not a different tool. The web UI is the primary interface for everyone; VS Code is for git, notebooks and files; the terminal is for heavy users. Roles: model-monitoring data scientist, AI engineer, data engineer, MLOps engineer, data scientist, data analyst, BI analyst, PO, agile coach, coordinator, platform developer. The jobs per role are hypotheses to confirm in interviews.

### Evidence from quenching (2026-10-24)

- `start` and `target` already exist as spec state (`plugins/quenching-specs/assets/specs/schema.json`), but dependencies exist only as `after:` between the items of one epic (`plugins/quenching-specs/assets/bin/quenching/specs/parse/epics.py`) — hence S5 before the Gantt (S9).
- Evals exist only for `components:hook:new` and `components:agent:new` (`plugins/*/assets/evals/components/**/evals.json`, Claude plugin-eval format) — hence S2 before H1 (S6).
- A per-harness port already exists for Codex (`plugins/quenching-codex`, `scripts/sync_codex_plugin.py`) — the pattern S3 follows for OpenCode.
- The Azure Boards backend already stores a whole spec in one work item: `System.Description` written as Markdown on every write, measured ceiling 1,048,576 characters, and `start`/`target` mapped to `Microsoft.VSTS.Scheduling.StartDate`/`TargetDate` (`plugins/quenching/assets/bin/quenching/specs/backends/azure.py`). It has no predecessor links for `after:` — hence S29 — and `cq specs migrate` only moves a tracker onto git (`--to git`) — hence S28.
- The git store's cost to a repository's global view, measured on quenching's own branch: 7,382 commits, 1,644 of them in the last seven days — the reason specs move to a tracker (Azure Boards for the adopter, GitHub Issues for the open projects) and off the branch.
- `validate` refuses an epic item whose `spec:` is not in the epic's own store (`parse/epics.py`) — hence S1 first; S1 shipped `spec: <owner>/<repo>#<id>` members (`specs/members.py`), so `## Tasks` lists every member with its real `after:` edges.

## Alternatives Considered

- **Frontier model only.** Several times the cost target; subscriptions hide the gap — per SemiAnalysis a Max plan delivers 12 to 63 times its price in API value — so the migration only closes with a cheap default model.
- **Managed Omnigent on Databricks.** In Beta, documented for AWS, no Python policies, no own key in the Sandbox: a reference, not a base, since the chosen path is self-hosting on a VM in the private network.
- **Running the compose directly on Databricks.** Dropped: costs more, gains little.
- **Provisioned throughput for Flash.** The 50-unit minimum only breaks even with pay-per-token around 160–175 billion tokens per month, about five times the estimated team volume.
- **Specs on a git branch of each code repository (quenching's default store).** Fast and unbounded, but every spec write is a commit: 1,644 in seven days on quenching's own branch, which floods the repository's global view for anyone outside the agent's loop. Dropped for every store on 2026-10-24: the adopter uses Azure Boards, the open projects GitHub Issues, and the git backend retires last (S33).
- **A self-hosted tracker (OpenProject, Plane) beside the git store, kept in sync.** Two stores need per-field ownership and a sync engine; single sign-on over OIDC is a paid edition in both; Azure Boards already holds the adopter's backlog with Markdown descriptions, native timelines, an official MCP server and the Copilot coding-agent handoff.
- **Seven new repositories, one per project.** The discovery split the platform into tempering, crucible, ingot, assay and pyrometer beside forge and hallmark. Dropped on 2026-10-24: seven release trains, CIs and stores are too much for a single maintainer, and the specs service belongs with the rules core it serves. So it lives in quenching, policies and cost in forge, and models and data operations in hallmark.
- **The specs service in forge, or quenching depending on forge.** Dropped: quenching must keep working on a workstation with no infrastructure, so the service runs over stdio from quenching itself and forge only hosts its HTTP deployment.
## Open Decisions

- **Catalog engine, build vs adopt** (spike): build hallmark on a metadata generator like the one the reference monorepo already has, or index an existing catalog such as OpenMetadata or DataHub.
- **H1 quality threshold** against the Claude baseline, and whether Haiku 5.5 replaces Flash for the light tier.
- **Omnigent upgrade policy:** Omnigent is alpha, so the platform needs a rule for how it is upgraded and who approves each version.
- **Persona jobs** are hypotheses until the interviews confirm them.
- **GitHub Projects:** Issues only for now; revisited if the open projects need a board beyond quenching's own interface.
## Risks

- **Omnigent in alpha:** API and configuration format may change — pin the version and keep a thin adaptation layer.
- **Managed version in Beta:** documented for AWS only; used as a reference, not a base.
- **OpenCode + Flash unmeasured:** if H1 lands below the baseline, Pi is the next candidate and routing turns hybrid.
- **Windows workstations have no sandbox:** agents run in containers on a Linux VM; people access through web, VS Code or a remote terminal.
- **Audit gap:** Omnigent's audit log is undocumented; the gateway and telemetry must cover it.
- **Leakage into the open projects:** a leak gate in each project's CI, the same rule as bricksmith.
- **Azure DevOps Services is a cloud store:** compliance must accept the specs there, as it accepted cross-Geo processing (H2); Azure DevOps Server on-premises has no remote MCP server, so the specs service stays the agents' only path either way.
- **Tracker latency:** taken as comparable to the git store (human's direction, 2026-10-24); S11's read cache absorbs it if it is not.
- **Cross-repository members over trackers:** `specs/members.py` resolves a foreign member only through a git mirror, so once a store moves to a tracker its members read as `unreadable`; S33 must give tracker stores that resolution before the git backend goes.
- **Scope vs capacity:** two new projects, quenching's specs service and the quenching adaptation depend on a single maintainer in spare time. Folding seven projects into three repositories (2026-10-24) cuts the release trains, CIs and stores to maintain, and the roadmap sequences by risk.

## Discoveries

- quenching has no verb to type an existing spec as an epic: `workItemType` is fixed at creation and `cq specs epic add` refuses an untyped spec, so forge spec 1 was typed by a direct frontmatter commit on the quenching branch (2026-10-24); a `cq specs type` verb or `epic add` offering to type the epic would avoid that.
- `cq specs new --json` is the only way a capture script recovers the new id; the plain output prints it only in prose — confirm the JSON shape is a stable contract before tempering wraps it (S4).
- **The DeepSeek endpoints are deprecated on Azure Databricks (checked 2026-10-24):** `databricks-deepseek-v4-1-flash` and `databricks-deepseek-v4-flash-0731` show READY in the `ia` workspace, but every call answers `BAD_REQUEST: This endpoint ... is deprecated`, and no `-1017` endpoint is listed. As delegated owner, H1 (S6) takes **GLM 5.3 Flash** (`databricks-glm-5-3-flash`, the open fallback in §Model routing) as its subject, with Haiku 5.5 still the light-tier candidate. §Model routing changes once S6 reports its numbers.
