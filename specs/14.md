## Problem

In the H1 spike (S6, spec 2) the Opus 5.5 grader cost about US$ 3.34, more than every agent arm together (US$ 2.18), so each future eval round pays mostly for grading. Re-grade the 36 saved H1 cases (`spikes/h1/results/**`: each case's output and snapshot, with the re-runs merged) with Flash 1017 through Unity Gateway as the grader, without running any agent again, and compare its verdict per assertion with the Opus verdicts already recorded: agreement rate, the disagreements listed, and US$ measured. The human capped the epic's Databricks model spend at US$ 10 in total on 2026-10-24 (about US$ 6 spent by S6) and allowed only this test: stop before any call that would take this spec past US$ 1. If agreement is high enough, the eval runner's default grader becomes Flash; otherwise Opus stays.

Member of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A grading-only harness re-grades the 36 saved H1 cases (4 arms x 9 cases, re-runs merged over the lost cases) with Flash 1017 through Unity Gateway, building the material and the grader prompt exactly as the eval runner does and running no agent.
- Every call runs inside the spike's disposable container, one at a time, with host and token minted from the Databricks profile at run time and never written to a file.
- A cost ledger prices one call first, projects the total, and refuses any call that could take the spec past US$ 1; measured tokens and US$ per call are recorded.
- A per-assertion comparison of the Flash verdict against the recorded Opus verdict gives the agreement rate overall, per arm and per suite, and lists every disagreement with the evidence each grader quoted.
- A short report states whether Flash may become the eval runner's default grader under a stated threshold, with the measured US$ against the US$ 1 cap.

## Out of Scope

- Running or re-running any agent arm: ruled out by the owner's instruction; the 36 outputs and snapshots are the fixed input.
- Changing the eval runner's default grader in the quenching repository: that is a change in another repository; this spec only recommends it with evidence.
- Grading with GLM, Haiku or Sonnet: only Flash 1017 was allowed within the budget.
- Re-grading with Opus: its verdicts are already recorded, and a second Opus pass would spend what the cap forbids.
- Measuring grader stability across repeated calls on one case: it would multiply the cost; sampled once, named as a limit in the report.

## Design

- **Same input as Opus saw.** The prompt is the eval runner's grader prompt and the material is its `material_of` (agent output then workspace snapshot, each tail-cut at 60000 characters), so only the grader model differs. The reply is checked with the runner's own rule: a verdict whose evidence is not a verbatim excerpt of the material is `unknown`.
- **Recorded verdicts are the merged ones.** For each case the verdict is the re-run's when one exists, as `report.py` does; cases the Opus grader failed on in the original run and that were never re-run keep their recorded `unknown`.
- **Grading runs in the container, as a plain call.** The image already holds python3, so the call is a `docker run --rm -i --entrypoint python3` with no bind mount: the request goes in on stdin, the answer comes out on stdout, the token travels by variable name only and is never in argv. No OpenCode and no agent loop runs, so the grader cannot act on the workspace.
- **One call at a time, and the cap is code.** The driver is sequential. Before each call it adds the worst-case price (estimated input at the input rate plus the `max_tokens` cap at the output rate, reasoning counted as output) to the measured total; if that exceeds US$ 1.00 it stops and says so. The first call is priced alone and the 36 are projected from it.
- **Price table.** Flash 0.30 input, 0.03 cache read, 1.20 output, in US$ per 1M tokens, from `spikes/h1/prices.json`.
- **Agreement is per assertion on the result triple** (`pass`, `fail`, `unknown`). Two derived views are reported: case approval agreement (all assertions pass) and the risky direction, Flash passing what Opus failed.
- **Threshold, proposed for the owner.** Flash replaces Opus as default grader if per-assertion agreement is at least 95% and Flash never passes an assertion Opus failed on a case whose failure was real. The report states the rule next to the number; the owner confirms or replaces it.
- Binding contracts: the unchanged `spikes/h1` disposable-container rule, the leak gate (no host, name, email or absolute home path in any file or message), and the US$ 10 epic cap of which this spec may spend US$ 1.

## Alternatives Considered

- **Run the runner's own grading path (`run_evals.py` with the OpenCode grader profile).** Rejected: it starts an agent harness for a task that needs one HTTP call, costs extra tokens for tool definitions and could act on files; the plain call is cheaper and cannot run an agent.
- **Run grading on the host with curl.** Rejected: the owner required the disposable container, and the token would sit in a host process environment longer.
- **Parallel calls.** Rejected: the owner required one call at a time, and a cap check needs the previous call measured.
- **Re-grade a sample of the cases.** Rejected: 36 cases are small enough to afford inside US$ 1 at Flash prices, and a sample would weaken the agreement number.

## Open Decisions

- Whether 95% agreement is the right threshold: decided by the owner when reading the report, with the measured disagreement list in hand; the report gives the number under 95% and under the stated alternative of 90%.
- Whether Flash's reasoning tokens make the real price exceed the estimate: decided by the first priced call; if its projection is above US$ 1 the run stops and returns a partial comparison, flagged as such.

## Risks

- A single Flash call is not repeatable at temperature above zero, so one disagreement may be noise: ACCEPTED — one sample per case is all the cap allows; the report names it a limit and lists the disagreements for reading.
- A reasoning model may spend its whole `max_tokens` on reasoning and return no JSON: mitigated by a generous cap counted into the worst-case price, and an unparsed answer is recorded as `unknown` for its assertions and counted as a disagreement, not retried silently.
- The token or host leaking into a file, the ledger or a commit message: mitigated by minting both at run time, passing the token by variable name, storing only content and token counts, and running the grep above before every commit.
- Spend over the cap: mitigated by the pre-call worst-case check being code, the first call priced alone, and the stop condition before each later call.
- Opus `unknown` verdicts left in the recorded set inflate disagreement: mitigated by reporting them as their own class, apart from pass/fail flips.
