## Problem

forge is public and is built next to an adopter's real environment, and on 2026-10-24 its first spike branch nearly published a corporate author email and an Azure Databricks workspace host; the conductor rewrote it before the push. Nothing in the repository stops that today: the only protection is an interim hook outside it (`core.hooksPath` set by hand), and forge has no CI at all, so a PR has no check to certify it and the steward cannot merge without a human (PR #12, 2026-10-24). Adopt the leak gate quenching ships (`holetz/quenching#2097`, modelled on bricksmith's ADR 0003) — generic patterns built in, a private denylist outside the repository that fails closed, `pre-commit` and `pre-push` hooks that also check the author and committer email — and add a minimal GitHub Actions workflow that runs the generic patterns plus gitleaks on every PR. The human asked for this protection in every repository of the project on 2026-10-24, which authorizes the hooks and the CI workflow.

Member of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A commit whose staged content or author email leaks is refused by a `pre-commit` hook shipped in the repository.
- A push whose commits (added lines, messages, author and committer emails) leak is refused by a `pre-push` hook shipped in the repository.
- Both hooks fail closed: without the private denylist, or without `cq` on the PATH, they refuse instead of passing.
- A pull request runs a minimal GitHub Actions workflow that scans for the generic patterns and runs gitleaks over the history.
- One repository gate, `bash scripts/verify_repo.sh`, runs the checks that need no private file, and CI runs it.
- CONTRIBUTING.md documents how to install the hooks and where the denylist lives.

## Out of Scope

- Changing git config (`core.hooksPath`) in any checkout: the document tells the contributor the command, nothing sets it. The interim hook outside the repository stays the human's to remove.
- Reading, copying or describing the denylist: it stays at `~/.config/quenching/denylist.txt` and never enters the repository, a log or a commit.
- Vendoring quenching's `leak.py` or `cq` into forge: the dependency points from forge to quenching only, never the reverse.
- Rewriting history already published; this spec guards what comes next.
- Any other CI job (lint, tests, builds): forge has none to run yet.

## Validation

- `bash scripts/verify_repo.sh` exits 0 on the final tree and prints each step it ran.
- `bash scripts/test-leak-gate.sh` exits 0: in a temp repository a staged CPF is refused by `pre-commit`, a clean change is accepted, a missing denylist refuses (fail closed), and a push carrying a CPF is refused by `pre-push`. The test points `QUENCHING_DENYLIST_FILE` at a temp file with a dummy term and never reads the real denylist.
- `bash scripts/leak-generic.sh` exits 0 on the tree and non-zero on a file carrying a CPF, a CNPJ, an Azure Databricks host, a `dapi` token, a cluster id or a private key header.
- Every `uses:` in `.github/workflows/ci.yml` ends in a 40-character SHA, and the workflow declares `permissions: contents: read`.

## Design

**The hooks call the installed `cq security leak`; nothing is vendored.** forge may depend on quenching and the plugin is the maintained home of the patterns, the email check and the fail-closed denylist; a copy would drift. The hooks resolve `cq` with `command -v` and refuse (exit 1, message) when it is absent, so a missing tool never reads as green. They run `cq security leak --staged --root "$ROOT"` and `cq security leak --pre-push --remote "$1" --root "$ROOT"`, modelled on quenching's `scripts/githooks/`. The denylist path is the one `cq` resolves (`$QUENCHING_DENYLIST_FILE` or `~/.config/quenching/denylist.txt`); forge code never opens it.

**CI cannot use `cq`, so it uses a small standalone script plus gitleaks.** `scripts/leak-generic.sh` greps tracked files with the same six generic patterns (CPF, CNPJ, Azure Databricks host, `dapi` token, classic cluster id, private key header). It is a deliberate duplicate of publishable patterns, not of the denylist; the two must be kept aligned by hand and the script says so in its header. gitleaks runs through `gitleaks/gitleaks-action` pinned to a commit SHA with `fetch-depth: 0`, so the history is scanned.

**Workflow rules.** Triggers: pull requests and pushes to `main`, ignoring the `quenching` data branch. `permissions: contents: read`; every action pinned by SHA with the version in a comment, as quenching's `ci.yml` does (checkout `3d3c42e5aac5ba805825da76410c181273ba90b1` v7.0.1; gitleaks-action `e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e` v3.0.0). The owner is a user account, so the gitleaks action needs no license key.

**The gate.** `scripts/verify_repo.sh` runs `bash -n` over the shell scripts, the behavioural test and the generic scan. It needs neither `cq` nor the denylist, so CI runs the same file.

**Install is documented, never done.** CONTRIBUTING.md gives `git config core.hooksPath scripts/githooks` as the contributor's own command.

## Alternatives Considered

- Vendor `leak.py` into forge: rejected, it drifts from the maintained copy and doubles the surface a pattern fix must reach.
- Hooks as thin wrappers over the gate script only (no `cq`): rejected, that loses the author/committer email check and the fail-closed private denylist, which are the reason for the spec.
- A `pre-commit` framework config: rejected, adds a Python tool and a second install step for two shell hooks.
- Gitleaks alone in CI: rejected, the Brazilian ids and Databricks hosts are not in its default rules.

## Open Decisions

- Whether to add a `.gitleaks.toml` with project rules: decided when the first gitleaks run on a PR reports a false positive; until then the default rules stand.
- Whether the `windows` hook path needs a `.cmd` shim: decided if a contributor on Windows reports it; the hooks are bash.

## Risks

- A contributor skips installing the hooks, so the local gate is absent: mitigated by CI scanning every PR with the generic patterns and gitleaks. ACCEPTED — the denylist terms are private and CI cannot check them.
- The generic patterns in `scripts/leak-generic.sh` drift from quenching's: mitigated by the header note and by the test using one sample per pattern.
- `cq` missing on a machine blocks every commit: intended (fail closed); the message names how to install it.
- The gitleaks action changes behaviour under a moving tag: mitigated by the SHA pin.
