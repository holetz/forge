## Problem

Adopters already enforce rules through Claude Code hooks (for example, refusing compute outside an approved cluster, or column overrides outside a registry); on the platform those must become policies or stay harness-bound. Port two such guard patterns to generic policies and check they produce the same blocks with no new false positive.

Formerly holetz/crucible#2.

Member S17 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- Two synthetic Claude Code `PreToolUse` hooks exist in the repository as the baseline: a compute guard (refuses a run aimed at a cluster outside an approved list) and a column-override guard (refuses a column override outside a registry).
- The same two guard patterns exist as Omnigent function policies (`compute_guard`, `column_override_guard`) in a spike module that follows the S16 mechanism: `policy_modules`, a `policies:` mapping, `type: function`, `factory_params`, `POLICY_REGISTRY`.
- One shared corpus of synthetic tool calls (blocked, allowed, hard) runs through both the hook and the policy; the test shows the same blocks, no new false positive, and names every divergence.
- The pinned Omnigent server's own loader (tag v0.19.1) resolves both policies from the spike config and they return the expected verdicts.
- `spikes/h6/REPORT.md` states whether H6 holds, which parts hold only partly, and what stays in the harness.

## Out of Scope

- Any adopter's real hook, cluster name, table, column, host or registry: every value is synthetic, and the repository is public.
- Shipping the two guards in the generic pack (`policy/`, `policy/config.yaml`, its defaults): a spike proves feasibility, adopting them belongs to an overlay or a later spec. `policy/` stays untouched, so the render drift check is unaffected.
- A Databricks call, a paid model call, or a live agent session: events are synthetic and the proof calls the loader only.
- Hooks on events a policy has no phase for (session start, notification, prompt submit): the report lists them as harness-bound, it does not port them.
- Any CI workflow, permission or grant change: `.github/` is untouched.
- Replacing the harness hooks: they stay on for the Claude Code harness, the policy is the platform-side layer.

## Design

**The mechanism is S16's, not a new one.** A spike module `h6_policies` exposes two factories, `compute_guard(approved_clusters, ...)` and `column_override_guard(registry, ...)`, each returning `evaluate(event) -> {"result": "DENY", "reason": ...} | None`, registered through `POLICY_REGISTRY` and listed in a spike `config.yaml` (`policy_modules`, `policies:`, `type: function`, `handler`, `factory_params`). The module is stdlib-only and imports nothing from `omnigent`, as `forge_policies` does, and reuses its shell parsing approach (`shlex` per command segment, shell tool names, `data.arguments`).

**Event shapes differ and the port maps them.** A hook receives `{tool_name, tool_input}` on stdin and blocks with exit 2 and a stderr reason; a policy receives `{type: "tool_call", target, data: {name, arguments}}` and returns DENY. The corpus stores one neutral case (tool name, arguments, expected verdict) and a small adapter builds each shape, so the comparison is on the decision, not on plumbing.

**The two patterns (synthetic).**
- Compute guard: a `synthcli compute ...` shell command, or an MCP tool call, whose cluster argument (`--cluster-id`, `--cluster`, `cluster_id`) names a cluster outside `approved_clusters` is refused; `synthcli compute create` is always refused. A call that names no cluster is not this guard's business.
- Column-override guard: `--override-column <table>.<column>=<value>` (or the MCP argument `column_override`) is refused unless `<table>.<column>` is in the registry.

**The registry is data, not code.** The hook reads `registry.synthetic.json` at run time; the policy takes the same lists as `factory_params` (rendered into the config), because the server process has no harness working directory. Whether a policy may read a mounted registry file at evaluation time is parked as an open decision.

**The baseline hook is written the idiomatic way**, as a stdin-JSON Python script with regular expressions, so divergences against the shlex-based policy are real findings rather than a constructed contrast. Each divergence stays in the corpus as `known_divergence` with its reason; the test fails on an unlisted divergence and on a listed one that stopped diverging.

**The proof uses the pinned loader, not compose.** `prove-loader.sh` runs `docker run --rm` on the Omnigent image pinned in `compose.yaml` (same tag and digest, read from the file), mounting the spike policy directory read-only and setting `OMNIGENT_CONFIG` and `PYTHONPATH`. Running the single image avoids the database, dex and router, so no stack, volume or port is created; `docker compose down -v` is run as a no-op safety only if a smoke stack exists. It follows `smoke-local.sh`'s disk guard and removes the image only if this run pulled it.

**Binding contracts.** `policy/` and `docs/policy-pack.md` are not rewritten; the pinned source (v0.19.1) defines the handler contract; the repository is public, so fixtures use `synthcli`, `team-a-*` style names and no real shape that `scripts/leak-generic.sh` matches.

## Alternatives Considered

- **Add both guards to the generic pack now.** Rejected: the guards depend on adopter vocabulary (a compute CLI and a registry file), so the generic pack would carry adopter-shaped defaults; the spike answers whether the port works first.
- **Judge H6 from the Omnigent documentation alone.** Rejected: the hypothesis says "same blocks, no new false positive", which only a run over a corpus can show.
- **Run the proof through the full compose smoke.** Rejected: it adds postgres, dex and the router for a loader call; a single container proves the same thing with less disk and no teardown risk.

## Open Decisions

- Whether a policy may read its registry from a mounted file at evaluation time instead of from rendered `factory_params`. Decided by the report: the spike implements the rendered form and records what the file form would need (a reload story for edits).
- Whether the guards graduate into the generic pack or an overlay slot. Decided after the report, by the human, in the epic hypothesis table update.
- Why now / what would make the spike not worth doing: the epic sequences S17 after S16 and H6's fallback ("keep the hooks in the harness") is cheap, so the spike is worth running only until the corpus answers; assumed from the epic, not asked.

## Risks

- **A corpus written by the same author flatters the port.** Mitigation: the hook is written first and idiomatically, hard cases (quoting, env prefixes, chained commands, equals form, sudo) are in the corpus, and divergences are reported, not smoothed.
- **The loader proof needs an image pull.** Mitigation: the disk guard aborts under 8 GB remaining, only a pulled image is removed, no other container is touched, and nothing runs in parallel.
- **A fixture trips the leak gate.** Mitigation: fixtures avoid real shapes (hosts, cluster-id shape, tokens); a flagged literal is fixed at the source, never bypassed.
- **ACCEPTED — policy and hook still share one author's regex-versus-shlex view of a shell command**, so a bypass neither catches (encoded command, script file) is not measured; the pack's Limits already state that pattern checks are bypassable.
- **Omnigent is alpha.** Mitigation: the proof runs on the pinned digest; the upgrade rule of `docs/policy-pack.md` applies.
