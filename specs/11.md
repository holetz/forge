## Problem

Cost has three sources — LLM through the gateway, Databricks compute and Genie agents — and no single view per person or team. Sum `system.ai_gateway.usage` and `system.billing.usage` into cost per person, team, session and project, compare against budgets and raise alerts, served over MCP for the coordinator's panel. Depends on the forge local profile (forge epic S13).

Formerly holetz/ingot#1.

Member S21 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A cost service in `server/cost/` totals spend per person, per team, per session and per project from two sources: gateway token usage (shape of `system.ai_gateway.usage`) and Databricks compute and agent usage (shape of `system.billing.usage` priced by `system.billing.list_prices`).
- The service is an MCP server (JSON-RPC 2.0 over HTTP, `tools/list` and `tools/call`) whose tools return those four views, plus a budget check that returns alerts when a person, team or project passes its warning or cap.
- Everything is built and tested against synthetic fixtures (JSON shaped like the system tables, loaded into an in-memory SQLite database). No code path in the repository opens a Databricks connection; the source is an injected reader.
- `docs/cost.md` documents the assumed table shapes, the pricing rule, the tool contract, and the live query as a later human step with a cost estimate to approve first.
- `scripts/verify_repo.sh` runs the cost tests, so the gate covers the service.

## Out of Scope

- Querying Databricks, a SQL warehouse, or any paid model: no warehouse is authorized, and a live run is a later human step with its own estimate. The reader port is where it will plug in.
- Blocking spend. Enforcement stays in Unity Gateway limits and the Omnigent `cost_budget` policy; this service reports and alerts.
- A compose service, CI workflow or grant change: deployment wiring waits for the live reader (a workflow change would be needs-human).
- The coordinator's panel UI: only the MCP surface it reads.
- Authenticating the MCP caller: the service binds to the internal network behind the egress gateway like the registry; end-user authentication is the open follow-up recorded in spec 24.

## Design

**One reader port, one SQLite model.** `cost.py` defines a reader interface returning rows (dicts) for the two tables and the price list. The only implementation is the fixture reader (JSON file or the generated default). Rows are loaded into an in-memory SQLite database, and the aggregations are SQL `GROUP BY`s, so the same queries port to the warehouse later with a dialect check. Rule: nothing in `server/cost/` imports a Databricks SDK or opens a connection.

**Assumed table shapes (to verify at the live step).** Gateway rows: `request_id`, `event_time`, `requester` (an opaque user id), `endpoint_name`, `input_tokens`, `cache_read_tokens`, `output_tokens`, and a `tags` map carrying `session_id` and `project`. Billing rows follow the documented `system.billing.usage` columns: `record_id`, `usage_date`, `sku_name`, `usage_unit`, `usage_quantity`, `identity_metadata.run_as`, and `custom_tags` with `session_id` and `project`. Prices: `system.billing.list_prices` gives a price per SKU. The real gateway table's column names are not confirmed by this repository, so the assumption is documented and the fixture builder is the one place to adjust.

**Pricing.** Gateway cost is tokens times the per-million rate of the endpoint, held in a model price table (input, cache read, output; the rates in spec 1's routing table, DBU list price at US$ 0.07). Billing cost is `usage_quantity` times the SKU list price. An endpoint or SKU with no price is not zero: its rows are counted in an `unpriced` bucket reported in every answer, so a missing price cannot read as a cheap day.

**Attribution.** Person is the requester or `run_as`. Team comes from a person-to-team map (`people.json`-shaped fixture), not from the tables; a person not in the map belongs to the team `unassigned`. Session and project come from the row tags; absent tags go to `untagged`. Every view therefore sums to the same grand total, and a test pins it.

**Budgets and alerts.** `budgets.json` holds, per scope (person, team, project) and name, a monthly cap and a warning fraction. `budget_status` returns each scope's spend, fraction, and a level (`ok`, `warning`, `over`). It only reports.

**MCP surface.** Stdlib `http.server`, JSON-RPC 2.0 on `POST /mcp`: `initialize`, `tools/list`, `tools/call`; tools `cost_by_person`, `cost_by_team`, `cost_by_session`, `cost_by_project`, `budget_status`, each taking an optional ISO `since`/`until`. Unknown methods and tools return JSON-RPC errors, never an exception trace. Same style and port convention as `server/mcp/registry.py`.

**Binding contracts.** Public repo: synthetic names only (`person-a`, `team-x`), no host, token, email or corporate term; fake literals are assembled at run time if a test needs one. No file sits under a directory named `hooks/`. The gate stays `scripts/verify_repo.sh`.

## Alternatives Considered

- **DuckDB fixture file:** rejected because it is not installed and adds a dependency to a stdlib-only service; SQLite gives the same SQL.
- **Query Databricks directly, small scope:** rejected by the human: no warehouse is authorized, and the live step needs a cost estimate first.
- **Compute cost in Python over lists, no SQL:** rejected because the real tables are large and the aggregation belongs where the data is; SQL keeps the port faithful.
- **Fold into the existing MCP registry process:** rejected because the registry is an inventory of other servers, not a place to host one.

## Open Decisions

- **Real column names of `system.ai_gateway.usage`:** decided at the live step by a `DESCRIBE` on the table (a zero-cost metadata call) run by the human, then the fixture builder and the reader are adjusted.
- **How a person maps to a team in production:** decided with the adopter; the fixture uses a map file, and the live source may be Unity Catalog groups.
- **Deployment as a compose service and registry entry:** decided after the live reader exists, since a service with only fixtures should not be shipped to the server.

## Risks

- **Pricing drift** (list prices change): the price table carries its date, and the live reader prefers `system.billing.list_prices` over the static table.
- **Assumed schema wrong:** ACCEPTED for this slice, because the live check is a named human step and the reader port confines the change.
- **Unpriced rows silently low:** mitigated by the `unpriced` bucket in every answer.
- **Cost data is sensitive per person:** the service is not exposed beyond the internal network and has no caller authentication yet; documented in `docs/cost.md` and recorded as out of scope.
- **Leak gate trips on synthetic literals:** fixtures use neutral names and assemble any token-shaped string at run time.
