## Problem

On 2026-10-25 the human approved a hosting option: a Linux host on the private network, reached over SSH and called `<server-host>` in the repository. `scripts/smoke-server.sh` ran green there. The pilot (S25) needs the server profile running there persistently, plus a repeatable way to deploy, upgrade the pinned Omnigent version, roll back and back up Postgres and the audit sinks. None of this exists: the smokes bring the stack up and tear it down.

Ship `scripts/deploy.sh`. It takes an SSH target and a git ref from arguments or an untracked config, never from the repository.

- **Preflight on the host:** docker and compose versions, free disk, RAM, port collisions.
- **Deploy:** a clean checkout of the ref into a per-ref directory, a compose project of its own (`forge`), and loopback-only ports chosen to avoid what the host already uses.
- **Secrets:** generated on the host into a `.env` with mode 600 that never leaves it.
- **Upgrade and rollback:** an upgrade keeps the previous ref, so rollback is one command.
- **Backup:** a `pg_dump` and a copy of the audit sinks into a dated directory.
- **Health:** a check that runs the non-destructive part of the server smoke against the running stack.

Model upstreams default to the stub. Switching to the Unity Gateway is a documented manual step, because it spends money and stays a human decision.

Done when deploy, upgrade, rollback, backup and health have run once on `<server-host>` and are recorded in the Outcome without the address, ending with the stack torn down or left on the stub, as develop decides. Unit tests or shellcheck cover the argument parsing and the preflight, and the gate and CI are green. The host's unrelated containers are never touched.

Member of holetz/forge epic 1 (before S25).

## Proposal

- `scripts/deploy.sh` exists with the commands `preflight`, `deploy`, `upgrade`, `rollback`, `backup`, `health` and `down`; the SSH target and the git ref come from arguments, the environment (`FORGE_HOST`, `FORGE_REF`) or an untracked `deploy.local.env`, never from a tracked file.
- Each release is a clean checkout of one commit in its own directory under the deploy root, and the server profile runs as the compose project `forge` on loopback-only ports that the preflight proves free.
- Secrets are generated on the host into a mode-600 `.env` that never leaves it; the script prints no secret and no host identity.
- An upgrade backs up first and keeps the previous release, so `rollback` is one command.
- `backup` writes a `pg_dump` and a copy of both audit sinks into a dated, mode-700 directory.
- `health` runs the non-destructive checks of the server smoke against the running stack.
- Model upstreams stay on the stub; `docs/deployment.md` documents the manual Unity Gateway switch and records one real pass of deploy, upgrade, rollback, backup, health and teardown, with every path relative to the deploy root and the host called `<server-host>`.
- `scripts/test-deploy.sh` covers argument and config parsing, ref validation, version comparison and port choice, and runs inside `scripts/verify_repo.sh`.

## Out of Scope

- Switching any upstream to the Unity Gateway: it spends money and stays a human decision, so only the documented manual step ships.
- A real IdP, TLS, a reverse proxy, hostnames and the host firewall rule: S25 and the operator own them; dex stays the dev provider and is reachable through an SSH tunnel only.
- The runner containers and the `agent-probe` service: the probe stands in for a runner in the smoke and has no role in a persistent stack.
- Backup retention, off-host copies and restore automation: `backup` writes a directory and a restore is documented as a manual `pg_restore`.
- Any CI workflow or grant change: none is needed, and one would stop the run with needs-human.
- Touching the host's unrelated stacks: no `docker system prune`, no `image prune`, no stop or restart of another project.

## Design

**Shape of the tool.** One bash file, `scripts/deploy.sh`. Run on the workstation it only parses arguments and then streams itself to the host with `ssh -o BatchMode=yes <target> bash -s -- --on-host <command> <args> < scripts/deploy.sh`; run with `--on-host` it performs the command locally on the machine it is on. The host therefore needs no copy of the script, and the script that ships is the one reviewed. Pure functions (`parse_args`, `read_config`, `version_ge`, `pick_ports`, `resolve_ref_ok`) sit above a `BASH_SOURCE == $0` guard so `scripts/test-deploy.sh` can source them.

**Configuration precedence** is argument, then environment, then `deploy.local.env`, then default. `deploy.local.env` is parsed line by line against a whitelist (`FORGE_HOST`, `FORGE_REF`, `FORGE_DEPLOY_ROOT`, `FORGE_REPO_URL`, `FORGE_PORT_BASE`) and is never sourced, so a stray line cannot execute. It is git-ignored. Defaults: deploy root `forge-host` under the remote home, repo URL the public holetz/forge origin, port base 18200.

**Layout under the deploy root** (all paths printed relative to it, so no home directory or user name reaches a log):

```
<root>/forge            object store: one clone, fetched, never built from
<root>/releases/<sha12> clean detached worktree of one commit; the compose project directory
<root>/current          symlink -> the running release
<root>/previous         symlink -> the release before it
<root>/.env             mode 600, generated once, shared by every release
<root>/backups/<UTC>/   mode 700: postgres.dump, audit.tar, telemetry.tar
```

*Existing clone.* `deploy` reuses `<root>/forge` when it is a git repository whose `origin` equals the repo URL and `git fetch` succeeds; otherwise it refuses and names `--replace-clone`, which moves it aside to `<root>/forge.replaced-<UTC>` and clones again. It never deletes.

*Compose project.* `docker compose -p forge --project-directory <root>/releases/<sha12> --env-file <root>/.env -f compose.yaml -f compose.server.yaml`. The fixed project name makes the named volumes (`forge_postgres-data`, `forge_audit-data`, `forge_telemetry-data`, `forge_artifact-data`) survive an upgrade and a rollback, while the bind mounts follow the release directory, so switching a release is `up -d --wait` from the other directory. Services: postgres, dex, stub, router, omnigent, egress, otel-collector, mcp-registry.

*Secrets and ports.* `.env` starts from the ref's `.env.example`, then gets fresh values for the OIDC client and cookie secrets, the Postgres password, the egress identity secret and the per-run upstream token (which also feeds `STUB_TOKEN`, as in the smoke), and four loopback ports from `pick_ports` (omnigent, dex, router, stub). `pick_ports` walks upward from the port base and skips what `ss -ltnH` lists as listening and what the previous `.env` already assigns to the project, so a host with many stacks needs no hard-coded exclusion list in the repository. Every upstream URL stays on the stub; the script never writes a Gateway URL or token.

*Preflight* (read-only, also the first step of `deploy`): docker server at least 24, compose plugin at least 2.24 (the overlay uses `!override`), `git`, `curl`, `openssl` and `python3` present, free disk at least `MIN_FREE_GB` (8) on the root's filesystem, `MemAvailable` at least 3 GiB (the sizing doc's server estimate), the chosen ports free. It prints facts and counts, not host identity.

*Upgrade.* Resolve the ref to a sha, take a backup, create the release worktree, point `previous` at the running release, `up -d --wait` from the new directory, then run `health`. A failed `up` or `health` exits 1 and prints the exact `rollback` command; nothing rolls back silently. *Rollback* swaps `current` and `previous` and runs `up -d --wait` from the restored release; it states that database changes made by the newer release are not reverted, which is why the upgrade backs up first.

*Backup.* `pg_dump -Fc` through `docker compose exec -T postgres`; the audit sink from the running egress container (`tar -C /audit`), and the telemetry volume through a one-off container of the already-pulled `python` image (the collector image has no shell). It prints the directory relative to the root.

*Health* needs no probe container: it checks that every service reports healthy, sends one request through the router on loopback and reads the stub's `/_last` to confirm the gateway credential arrived and the client's did not, confirms from inside the egress container that an unlisted upstream answers 403 and CONNECT answers 405, that the registry lists its entries through the gateway endpoint, and that the audit file holds the request's session id with `"identity":"router"`. The one request it sends adds one audit line; it changes no configuration.

*Teardown.* `down` runs `docker compose -p forge down --remove-orphans`, adding `-v` only with `--volumes`. It never removes images, so it cannot reach an image another stack shares.

**Binding contracts.** Published ports stay `127.0.0.1` (compose.yaml). The pinned image digests are not edited. `docs/audit-identity.md` still holds: the health check asserts what it already asserts. The gate's docs leak scan must stay clean, so the runbook names the host `<server-host>` and shows only relative paths.

## Alternatives Considered

- **Ansible or another configuration tool:** rejected; one more dependency on the host and the workstation for six commands, and the repository has none.
- **Copy the checkout with rsync instead of cloning on the host:** rejected; it ships the workstation's untracked files and the ref would no longer name what runs.
- **Run every smoke on the host as the deployment:** rejected; the smoke tears the stack down on exit and removes images, the opposite of persistent.
- **A systemd unit wrapping compose:** deferred; `restart: unless-stopped` already restarts containers after a host reboot, and a unit adds a root-owned file on a shared host.
- **Rollback by `git checkout` of the previous ref in one working directory:** rejected; it mutates the running release's files and cannot be undone without the ref.

## Open Decisions

- Whether the stack is left running after the pilot is decided now: it is torn down with `down --volumes` of the `forge` project only, because the human's closing instruction for this run is teardown; the backup directory is kept and its relative path recorded in `docs/deployment.md`. The Outcome states it.
- Which two refs of main the upgrade uses is decided at run time from `git log` of origin/main: the two newest first-parent merges that both contain `compose.server.yaml`; the shas go in the pilot record.
- The Omnigent version bump itself (a new pinned digest) is not exercised: the two refs of main may carry the same pin. The upgrade path is proven by the release switch; a digest bump is the same switch with a changed image line.

## Risks

- **A shared host.** The script could hit another stack. Mitigation: every docker call carries `-p forge` or a `forge_` volume name; `down` and `backup` never list or prune globally; the run compares the set of unrelated containers before and after.
- **Port collision after the preflight.** Another stack binds a chosen port in between. Mitigation: compose fails to publish and `up` exits non-zero; the preflight runs immediately before `up`.
- **Secrets in logs.** Mitigation: the script prints keys never values, `set -x` is never used, `.env` is mode 600 under a mode-700 root, and the test greps the script's output on a dry run for the generated values.
- **Host identity in a tracked file or log.** Mitigation: the target is read from the environment at run time, paths print relative to the root, the script never prints `hostname`, `whoami` or `$HOME`, and the tree and commit messages are grepped before the PR.
- **Rollback does not undo a schema migration.** ACCEPTED — the upgrade takes a backup first and the runbook says so; both refs of this pilot carry the same Omnigent pin.
- **Dex issues `dex.localhost` URLs, so a browser login does not work off-host.** ACCEPTED — the pilot proves the deployment mechanics; the IdP is S25's.
